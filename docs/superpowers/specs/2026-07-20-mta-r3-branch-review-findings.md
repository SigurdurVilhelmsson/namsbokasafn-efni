## [important | skeptic votes: minor, minor, minor] returnEditToPending resurrects an edit without superseding the segment's active acceptance
**File:** server/services/segmentEditorService.js 536-573
**Detail:** PR1's invariant is "a revision in flight supersedes the acceptance": `saveSegmentEdit` calls `acceptanceService.supersedeForEdit(book, moduleId, segmentId, conn)` on both the INSERT (line 171) and UPDATE (line 134) branches, and `propagationService.js:135` mirrors it. `returnEditToPending` (the "Opna aftur" path) flips a rejected/discuss row back to `'pending'` with a bare `UPDATE segment_edits SET status = 'pending' …` and never touches `segment_acceptances`. Before this branch that hole was unreachable in practice, because the client's `} else if (acceptance) {` chain meant an acceptance could not be created on a row that had any edit — so acceptance+rejected essentially did not exist. This branch makes acceptance-beside-rejected the headline supported state, which makes reopen the routine way to produce active-acceptance + active-edit: exactly the combination `acceptSegment` refuses to create (`EDIT_EXISTS`, acceptanceService.js:88-93). The attestation stays `status='active'`, keeps counting in the reviewed UNION and the `staðfest` stats chip, and the row renders "Bíður" and "Staðfest" simultaneously. It self-heals only if the edit is eventually approved AND applied (lapseDrifted); if it is rejected again, or sits pending indefinitely, the illegal state persists.
**Failure scenario:** Editor attests segment S (rejected edit present) → `segment_acceptances` row active. Head editor clicks "Opna aftur" on the rejected edit → status 'pending', acceptance untouched. The row now shows both the "Bíður" and "Staðfest" chips; `acceptEligibility.acceptBlockReason` returns 'EDIT_EXISTS' for a segment that already holds an acceptance. If a later apply runs while the edit is still pending, `stampApplied` stamps `applied_at` on an attestation whose segment has an unreviewed revision open, and `writeReviewStatusSidecar` records the durable status as `accepted` (acceptance is checked first) even though a head editor has an in-flight correction to those bytes.

## [blocking | skeptic votes: important, important, important] HUMAN_CONTENT compares raw edited_content against a NORMALIZED baseline — it fails open on trailing whitespace, single newlines and backslash escapes
**File:** server/services/acceptanceService.js 120-132 (mirror: server/public/js/accept-eligibility.js:41-43)
**Detail:** The guard is `... AND edited_content = ?` bound to `seg.is`. But `seg.is` is NOT the bytes stored in `segment_edits`. `loadModuleForEditing` builds it as `normalizeTermMarkers(en, unescapeMtMarkers(normalizeWraps(fileText)))` (server/services/segmentParser.js:126,155-157 → tools/lib/mt-normalize.cjs), while `applyApprovedEdits` writes `winner.edited_content` verbatim into the faithful file (server/services/segmentEditorService.js:996-1002 `content: overlay ? winner.edited_content : seg.is`) and then only stamps `applied_at` — it never rewrites `edited_content` to its normalized form (the only UPDATEs on that row are `SET applied_at = CURRENT_TIMESTAMP` and the supersede one). So whenever an editor's saved text is not already a fixed point of the normalizer, the round trip changes it and the equality silently misses. Verified empirically against the real code:
  'Halló heimur. '        -> 'Halló heimur.'        (trailing space stripped by parseSegmentRecords)
  'Fyrsta lína.\nÖnnur.' -> 'Fyrsta lína. Önnur.'  (normalizeWraps: single \n -> space)
  'Verð \\[x\\] hér'      -> 'Verð [x] hér'         (unescapeMtMarkers)
Nothing strips these on the way in: the route accepts the raw textarea value (server/routes/segment-editor.js:349-353 checks only presence and length) and the client posts `document.getElementById('textarea-...').value` unmodified (server/public/js/segment-editor.js:1286). Trailing whitespace and backslash escapes are the realistic mainline triggers (a virgin textarea is pre-filled with the already-normalized `seg.is`, so a single newline requires the editor to press Enter deliberately).

The damage is cross-consumer, exactly the class the campaign lesson names. Guard fails open -> the segment is accepted as MT -> `writeReviewStatusSidecar` checks acceptances FIRST (server/services/acceptanceService.js:361-367) -> the durable `{module}-review-status.json` records `status:'accepted', by:<attester>` instead of `status:'edited', by:<the editor who wrote it>` -> item 20b PR2's corpus export reads that record. A human translation is published to the research corpus as machine output attributed to someone who did not write it.

Why the branch's own defense misses it: the shared scenario table (server/__tests__/helpers/acceptEligibilityCases.cjs) uses `MT = 'Fyrsta efnisgrein.'` — no trailing space, no newline, no backslash. The parity mechanism proves the two gates AGREE; it cannot prove the rule is CORRECT, and here client and server fail identically, so parity stays green. Fix direction: compare against a normalized form of `edited_content` (run it through the same mt-normalize chain) rather than raw bytes, and add a normalization-sensitive row to the shared table.
**Failure scenario:** Editor saves an edit on m68664:para:fs-id01 as 'Vatn er hreint. ' (trailing space, or with an inserted line break, or containing '\[' ). Head editor approves; Vista+Birta applies it — the faithful file now holds the human text and `segment_edits.edited_content` = 'Vatn er hreint. '. On the next module load `seg.is` = 'Vatn er hreint.' (trailing space stripped). Both the client predicate and the SQL guard evaluate `edited_content === seg.is` as FALSE, so HUMAN_CONTENT does not fire; the row offers 'Staðfesta MT' and the POST succeeds. The next apply regenerates the sidecar, which now says {"m68664:para:fs-id01":{"status":"accepted","by":"attester"}} for a segment whose bytes are a human translation by someone else.

## [important | skeptic votes: minor, minor, important] "Opna aftur" (returnEditToPending) does not supersede an active acceptance — this branch makes acceptance + pending-edit reachable, and metrics count it reviewed
**File:** <repo>/server/services/segmentEditorService.js 536-573 (and server/public/js/segment-editor.js:894)
**Detail:** Every other path that puts an edit in flight kills the segment's acceptance: `saveSegmentEdit` calls `acceptanceService.supersedeForEdit(book, moduleId, segmentId, conn)` on BOTH its branches (segmentEditorService.js:134 and :171). `returnEditToPending` — the head-editor "Opna aftur" button, rendered on rejected/discuss rows at segment-editor.js:839 — flips `status = 'pending'` (line 562) and touches nothing else.

Before this branch that gap was unreachable: a rejected row never offered "Staðfesta MT", and saving an edit always superseded the acceptance first, so an acceptance could never sit beside an edit that a head editor could reopen. This branch's whole point is that a rejected row now offers accept (segment-editor.js:894 `} else if (!blockReason) {`), which creates the precondition.

The resulting state contradicts the service's own guard: `acceptSegment` refuses exactly this shape with `EDIT_EXISTS` ('Bútur er með virka breytingu í ferli — staðfesting á ekki við.', acceptanceService.js:88), yet the DB now holds an active acceptance on a segment with a pending edit. It also feeds the metrics that RISE: `getReviewedSegmentsByModule` (segmentEditorService.js:1367-1373) UNIONs `segment_acceptances WHERE status = 'active'` with no edit-status condition, so the segment counts as reviewed while a head editor is mid-re-review of it. Fix mirrors saveSegmentEdit: call `acceptanceService.supersedeForEdit(edit.book, edit.module_id, edit.segment_id, conn)` inside returnEditToPending's write (ideally wrapped in a transaction with the UPDATE), or refuse reopen while an acceptance is active. This is the same cross-STAGE class as PR1's four must-fixes (revoke↔sidecar, apply↔activity-log) — a new UI affordance meeting an old state transition nobody re-checked.
**Failure scenario:** Editor E edits segment s → head editor H rejects it → E (new in this branch) clicks "Staðfesta MT" on the rejected row, acceptance A becomes active → H clicks "Opna aftur" on the rejected edit. `returnEditToPending` sets the edit back to 'pending' and leaves A active. The module's reviewed count still includes s (UNION on active acceptances), the row shows "Bíður" and "Staðfest" side by side on a green background, and a fresh POST …/accept on s would 409 EDIT_EXISTS — the system is holding an attestation its own eligibility guard forbids, on a segment under active dispute.

## [minor | skeptic votes: minor, minor, minor] Icelandic plural agreement in noneLeftContested is wrong for counts ending in 1 (21, 31, 101…)
**File:** <repo>/server/public/js/ui-strings.js 104-112
**Detail:** The toast switches on `n === 1`:

    (n === 1 ? ' bútur með fyrri breytingu bíður' : ' bútar með fyrri breytingu bíða')

Icelandic number agreement follows the LAST digit, not the value: 21, 31, 41, 101 take the singular ("21 bútur … bíður"), 11 takes the plural. The current test produces "21 bútar með fyrri breytingu bíða staðfestingar", which is ungrammatical. Both the noun and the verb are in the switched fragment, so the whole clause agrees or disagrees together — the fix is one predicate: `n % 10 === 1 && n % 100 !== 11`.

The rest of the sentence is fine, and the quote convention `„Staðfesta MT"` (low opening quote, ASCII closing) matches the file's existing bytes in `unchangedNothingSaved` and `unchangedWithdrawConfirm`, so it is consistent even though it is not the strict Icelandic „…“ pair.
**Failure scenario:** A module with 21 contested rows (rejected or superseded edits) — plausible in a long chapter after a review round. The editor exhausts the keyboard stream, presses Ctrl+Shift+Enter, and gets: "Engir ósnertir bútar eftir — 21 bútar með fyrri breytingu bíða staðfestingar." Grammatically wrong Icelandic in the one toast whose job is to stop the editor believing the module is finished.
