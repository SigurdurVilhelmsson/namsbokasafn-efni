## 1. What this is, and what it deliberately is not

The segment save gate (`server/public/js/segment-validation.js`) detects **marker deletion and nothing else**. This design adds **four new invariants** (malformed shape, termination, unknown type, `lb`/`rb` pairing), **generalises the existing one** (count preservation, today implemented per named marker), and adds **a second consumer** that applies the absolute ones to committed content.

**It is not a rewrite of the validator.** `validateStructure`'s architecture — one rule set, `blocked` enforced server-side, `warnings` advisory — is correct and stays. **The gap is coverage, not design.**

**It is not a content repair.** Six real defects are known to exist in committed files (§2.3, §2.4). They live in `02-mt-output` and `02-for-mt`, which are READ-ONLY / generated by project rule. **Repairing them is separate scoped work and must not ride in on a validation change.**

**It is not a marker parser.** No marker tree is built. See §4.

### 1.1 Why now

The gap was measured, not theorised. **[measured-here], by executing `validateStructure`:**

| Input | Result |
|---|---|
| `[[xref:kafli\|1]]` → `[[xref: kafli\|1]]` (one added space) | `blocked: null` — **passes** |
| `[[MATH:1]]` duplicated | `blocked: null` — **passes** |
| `[[sub:]]` `[[i:]]` `[[xref:]]` `[[link:]]` `[[term:]]` deleted | `blocked: null` — **all pass** |
| `[[MEDIA:1]]` deleted *(control)* | blocks — `media-missing` |

The control is what makes the four negatives measurements rather than an absence.

## 2. The measured facts this design rests on

### 2.1 The full marker-type census — 17 types

**[measured-here]**, all books, `03-faithful-translation` + `02-mt-output`:

`sub` **10,739** · `i` 5,927 · `MATH` 4,649 · `sup` 4,143 · `MEDIA` 2,807 · `BR` 905 · `xref` 667 · `b` 557 · `em` 181 · `docref` 137 · `term` 100 · `link` 60 · `rb` 38 · `lb` 37 · `TABLE` 13 · `SPACE` 4 · `fn` 1.

**`sub` is the single most common marker in the corpus and has no protection today.** That one line is most of this item's value.

`rb`, `lb` and `TABLE` appear in **no documented marker table** (`.claude/skills/inline-markers/SKILL.md`), although `cnxml-extract.js` and `cnxml-inject.js` reference them. This is live proof that an unknown-type rule is needed rather than hypothetical.

### 2.2 Markers nest, legitimately

**[measured-here]: 315 occurrences.** A complete instance, quoted in full:

```
[[b:Some representations of butane, C[[sub:4]]H[[sub:10]].]]
```

Bold wrapping subscripts — a real need for chemistry formula labels.

⚠️ **Self-review note, worth carrying:** an earlier draft quoted this as `[[b:IE[[sub:1]]`, which is a **truncated grep match, not a marker**. It carries two `[[` and one `]]` and would *fail* rule 1b. **Using it as a "must stay silent" control would have encoded a broken fixture into the test suite.** Quote nesting examples only from a complete, balanced construct.

⚠️ **A `\[\[(\w+):([^\]]*)\]\]` regex mis-parses every one**, reading type `b` with content `Some representations of butane, C[[sub:4` and leaving the rest dangling. This constrains the implementation (§4) and is the single most likely way to get this wrong — the failure is silent and flags *correct* content.

### 2.3 Malformed markers already exist in committed content — producer: MT

**[measured-here]:** a corpus-wide scan for `[[type: ` (space after the colon) returns **5 occurrences**, against a **control of 29,657 well-formed markers** found by the same command.

- `efnafraedi-2e` ch06 `m68733` — `[[i: 3d;]]`
- `edlisfraedi-2e` ch04 `m42075` — 4× `[[b: …]]`

All five are in `02-mt-output`, none in `03-faithful-translation`. **[inferred]** the producer is therefore the MT step, not an editor.

**Provenance checked before indicting today's pipeline [measured-here]:** both files record `"tool": "api-translate"`, but both were written **2026-03-22/23**, in the commits that *introduced* bracket markers — one commit message reads *"bracket markers `[[i:]]` `[[link:]]` + re-translation → 110 PERFECT (was 102)"*, i.e. that run was explicitly not perfect. **[inferred]** these are migration-vintage artefacts and are **not** evidence that `/v1/translate` corrupts markers now.

⚠️ **This adds a second axis to CLAUDE.md's warning that marker-survival evidence is per-ENDPOINT: it is also per-VINTAGE.** The recorded survival evidence postdates this content and never covered it.

### 2.4 `lb` / `rb` are literal-bracket escapes — CONFIRMED from code, and the attribution corrected

**[measured-here] — the emitting code was located, so this is no longer an inference.** `tools/lib/exercise-html.js:44`:

```js
return text.replace(/[[\]]/g, (c) => (c === '[' ? '[[lb:]]' : '[[rb:]]'));
```

**`lb` = literal `[`, `rb` = literal `]`.** Its docstring gives the reason: a literal `[` immediately before an inline tag (`"[<i>α</i>]"`) collided with the marker it produced (`"[[[i:α]]]"`) and broke re-parsing — a corpus find, item 9 T7.

⚠️ **They are produced by the EXERCISE converter, not by `cnxml-extract.js`** — whose construction list is `MATH MEDIA SPACE TABLE b docref em fn i link sub sup term u xref` and contains no `lb`/`rb`. That is why the imbalance below sits in an `exercises-segments` file and why only the chemistry books carry these markers at all.

**[measured-here]:** corpus counts are **38 `rb` / 37 `lb`**, and the imbalance is real — `lifraen-efnafraedi` ch12 `exercises` has `lb=2 rb=3`, rendering a stray `]` (`2,4 × 10[[sup:6]] kJ/mól[[rb:]]`). It is present in `02-for-mt` (ENGLISH) as well as `02-mt-output`.

🔴 **ATTRIBUTION CORRECTED, and the correction matters for the rule's tier.** An earlier reading of this session — recorded in register §C53 ⑨ — called the imbalance a defect from a *third producer, extraction*. **The escaper is 1:1**: every `[` becomes `[[lb:]]` and every `]` becomes `[[rb:]]`, with no state and no pairing logic. An unmatched `[[rb:]]` therefore means **the SOURCE text carries an unmatched `]`**, faithfully transcribed. **This is a source-content asymmetry, not pipeline corruption.**

**Consequence: rule 4 is correctly a `warn` and `block` would have been wrong** — the segment is not damaged, and no editor action can or should "fix" a bracket the source never balanced.

**So the producer count stands at two, not three: MT (§2.3) and the editor (zero offences to date).** The argument for §6 is unchanged and if anything stronger — a save-only guard covers the one path that has never yet gone wrong, and the corpus check is what surfaces asymmetries that no save can introduce.

⚠️ **A THIRD AXIS ON MARKER-SURVIVAL EVIDENCE — per-marker-SHAPE — and it is a standing, unresolved caution written into the code.** `exercise-html.js`'s docstring: *"the content-bearing `[[i:...]]` family's proven ~100% Málstaður survival does NOT transfer for free to the empty-body `[[lb:]]`/`[[rb:]]` shape, which is new and API-unverified … **Probe survival before the first real MT run that can hit these markers.**"* Combined with §2.3, marker-survival evidence is now known to be per-**endpoint**, per-**vintage** and per-**shape**. **Out of scope here; noted so it is not rediscovered.**

### 2.5 The consumer count in the validator's own docstring is wrong

`segment-validation.js` says *"ONE rule set, three consumers"*. **[measured-here]** it is required by four:

```
server/routes/segment-editor.js
server/routes/localization-editor.js
```

**`propagationService` matters:** propagation applies one editor's change to *other* segments, so marker rules will automatically govern propagated edits. That is the desired behaviour, but it is a blast radius nobody had stated. **Correct the docstring as part of this work.**

| Existing | Where | Covers | Does not cover |
|---|---|---|---|

## 3. The taxonomy

Three tiers. Every one of the 17 measured types is classified; the unknown tier exists for the next extraction vintage, not for today's gaps.

| Tier | Types | Invariant |
|---|---|---|
| **atomic** | `MATH` `MEDIA` `TABLE` `BR` `SPACE` `lb` `rb` | count preserved **and** content byte-identical |
| **structural** | `sub` `sup` `xref` `link` `term` `docref` `fn` | count preserved; **content freely editable** |
| **presentational** | `i` `b` `em` `u` | count change **warns** |

**Why the tiers fall where they do — from what each marker *becomes*, not from taste:**

- **atomic** content is an index or id (`MATH:4`, `TABLE:fs-idm121830912`) or empty (`lb`, `rb`, `BR`) — a pointer, not prose. Byte-identity is therefore both correct and free.
- **structural** markers carry translatable prose but change meaning or navigation if dropped. `[[term:text|id]]` → `<term id="…">` where the id anchors a sidecar lookup; `[[sub:2]]` in H₂O; `[[xref:…]]` is a link target.
- **presentational** markers may legitimately differ between languages — Icelandic need not italicise what English did.
- `lb`/`rb` are **atomic, not structural**, and the distinction is load-bearing: atomic asserts byte-identity, which (their content being empty) is free and additionally catches an editor typing `[[rb: ]]`. **[inferred]** a bracket is language-invariant — `[(CH₃)₂CH]₂CuLi` is that formula in every language — so an editor never has a legitimate reason to drop one. This is the same argument PR #388 used for element symbols.
- `u` is retained at **zero** occurrences deliberately. Removing unused entries is how a taxonomy acquires false unknowns later; the cost of keeping it is one array element.

**Not encoded as a rule, though it is a real convention in the data [inferred]:** every uppercase type is atomic and id/index-anchored, every lowercase type is content-bearing. Inferring tier from letter case would be a guess dressed as a rule.

## 4. The rules

**All four are per-type COUNT scans over the `[[type` prefix. No marker tree is built.** This is what makes them immune to §2.2's nesting, and none of the four needs marker instances.

| # | Rule | Kind | Tier |
|---|---|---|---|
| 1a | **Malformed shape** — `[[type:` immediately followed by a space | absolute | **block**, all types |
| 1b | **Termination** — `[[` count equals `]]` count within the segment | absolute | **block** |
| 2 | **Count preservation** — baseline count > edited count (key per §4.2) | relative | **block** atomic + structural · **warn** presentational |
| 3 | **Unknown type** — a `[[type` the taxonomy does not name | absolute | **warn** |
| 4 | **`lb`/`rb` pairing** — counts equal within a segment | absolute | **warn** |

**Rule 1b is defined by bracket counts, not by parsing**, which is what makes it nesting-safe: a legitimate `[[b:… [[sub:4]] …]]` has equal counts, and so does every segment in the corpus today. **[measured-here]:** sampling a nested file segment-by-segment found **no unbalanced segment**, so this rule is satisfied by the current corpus and will fire only on new damage.

### 4.1 Absolute vs relative is the design's spine

**Rule 2 is relative** — it compares edited against baseline and therefore **inherits any defect the baseline already carried**. Rules 1, 3 and 4 are **absolute**: true of a segment in isolation.

**Only absolute rules can find pre-existing corruption.** Rules 1–3 would not have found §2.4's stray bracket, because count preservation faithfully preserves it. This is why rule 4 exists and why §6's corpus check is not a convenience.

It is also the module's public API (§5): the absolute rules are exactly the ones that work without a baseline, which is exactly what a corpus check has.

### 4.2 Rule 2 keys differently by tier — this is how byte-identity is enforced

**Self-review caught this: §3 declares byte-identity for the atomic tier, and a per-*type* count does not deliver it.** `[[MATH:4]]` → `[[MATH:5]]` leaves the `MATH` count at 1 and would pass.

So rule 2's key depends on the tier:

| Tier | Key | Catches |
|---|---|---|
| **atomic** | the **exact marker string** — `[[MATH:4]]` | deletion **and** mutation of the index/id |
| **structural**, **presentational** | the **type** — `sub` | deletion only; content stays freely editable |

One rule, one code path, a tier-dependent key. Nothing else changes.

#### 4.2.1 This SUBSUMES four existing rules — preserve their codes

`validateStructure` already implements exact-string presence for `[[MATH:N]]` and `[[MEDIA:N]]`, and per-type counts for `[[BR]]` and `[[SPACE]]`. Under §4.3 those four become special cases of rule 2.

**Collapse them into rule 2 rather than running both** — two rules reporting one defect under two codes is how a violation list becomes untrustworthy. ⚠️ **But keep emitting the existing codes** (`math-missing`, `media-missing`, `br-removed`, `space-removed`): they are consumed by `UI.validation` for editor-facing wording, and changing them is a client-visible change this spec does not intend.

⚠️ **Do NOT touch the non-`[[…]]` rules.** `[#CNX_…]`, `[text](url)` and `[doc#target]` are the chemistry-era dialect (§2.1 context) and are **not** bracket markers — rule 2 cannot see them, and they must keep their own rules.

### 4.3 Why rule 3 is a warning and not an error

The corpus keeps acquiring marker types nobody documented — §2.1 found three. **The design accepts incompleteness and makes it announce itself.** A new type that turns out to be structural gets its tier in a follow-up; until then it is visible rather than silent. Erroring would block a legitimate extraction change on a taxonomy update.

## 5. Module boundary

New `server/public/js/marker-integrity.js`, following the UMD pattern already used by `segment-validation.js` and `marker-highlight.js` (browser global + `module.exports`):

- `MARKER_TIERS` — the taxonomy
- `scanMarkers(text)` → `{ counts: {type: n}, malformed: [...], unknown: [...] }`
- `checkAbsolute(text)` → rules 1, 3, 4
- `checkRelative(baselineCounts, editedCounts)` → rule 2

`segment-validation.js` calls both and maps results into its existing `blocked`/`warnings` code shape. The corpus check calls `checkAbsolute` only. **One taxonomy, no second copy** — two copies would drift, which is this project's most repeated failure.

**Why a separate module rather than inlining:** one clear purpose ("what markers does this text contain, and is that well-formed"), independently testable, and requireable by the corpus check without dragging in the editor's rule set.

**Placement rationale:** `server/public/js/` already holds server-required modules (§2.5), which is how a rule reaches both browser and Node **without a build step**. Keeping the check under `server/` also avoids adding a new MIT → AGPL edge (CLAUDE.md known gap E-2); a `tools/` script requiring a `server/` file would create one.

The editor page gains a 13th `<script src>`, loaded **before** `segment-validation.js`.

### 5.1 SHARE THE DATA, NOT THE CODE — lead decision, 2026-08-12

§2.6 establishes that rule 2 already exists in `tools/api-translate.js`. The fork was whether to share the implementation or only the taxonomy. **Ruled: share the data.**

**One owner: `tools/lib/marker-types.json`** — type → tier, plus a flag for the colon-less types (`BR`, `SPACE`). It lives under `tools/` (MIT) so that every consumer reads it in the permitted direction; a `server/`-owned file would force `tools/` to reach into `server/`, which is CLAUDE.md's known gap E-2.

| Consumer | How it reads the taxonomy |
|---|---|
| `tools/api-translate.js` | ⚠️ its `BRACKET_MARKER_TYPES` array is **replaced by a derivation from this file**. Leaving it in place would make three copies, not two. |
| `server/scripts/check-marker-integrity.js` | `require()` |
| `server/public/js/marker-integrity.js` (Node side) | `require()` |
| the same module in the **browser** | an express static mapping serves the JSON — **no copy, no build step** |

**The counting logic is duplicated deliberately**: it is one regex per side, and forcing a browser-servable shared `.cjs` introduces more novelty than it removes. **The duplication is made safe by a cross-implementation consistency test** (§7.6) rather than by hoping.

**What must never be duplicated is the type list and the tier assignment** — those are facts, and facts are what drift here.

## 6. The corpus check

`server/scripts/check-marker-integrity.js`, beside `verify-b4b1-gates.js`.

**Trees scanned:** `02-for-mt` · `02-mt-output` · `03-faithful-translation` · `04-localized-content`.
Not `01-source` (CNXML, no markers), not `05-publication` (HTML).

⚠️ **Exclude `*.bak`.** The project's backup convention is `{filename}.{YYYY-MM-DD-HHMM}.bak`, and `04-localized-content` currently holds **only** a `README.md` and seven June backups — scanning them would report defects in files nobody reads. `eslint.config.js` already ignores `*.bak`; follow it.

**`04-localized-content` is empty of markers today and is included deliberately** — localization has not started, and per the lead (2026-08-12) it will carry **the same markers as the faithful text**, Icelandic-localized. Including it now means the gate is in place before the first localized file lands, rather than after.
**Including the ENGLISH `02-for-mt` is deliberate** — it is the only reason §2.4's defect was distinguishable from an MT one.

**Allowlist granularity: `(file, segmentId, rule)`.** Allowlisting by file alone would mask a *new* violation in a file that already has one — and `lifraen-efnafraedi` ch12 `exercises` is exactly such a file. Six known violations (§2.3, §2.4) are grandfathered in explicitly, making the debt countable rather than invisible.

⏰ **THE ALLOWLIST MAY NOT BE NEEDED AT ALL — SEQUENCING, added 2026-08-12 after §C56 was logged.** Five of the six known violations (§2.3) are **migration-vintage artefacts in `02-mt-output`**, and §C56's whole-corpus re-extract + re-MT **regenerates exactly those files**. **The order therefore matters more than the mechanism:** ① ship the **save-gate** half of this spec first — it is independent of corpus state and protects editing that continues through the migration; ② run §C56; ③ **then** baseline the corpus check against the regenerated corpus. **If it comes back clean, build no allowlist.** Building it first buys a grandfathering list for defects the migration deletes, and its own staleness report would flag every entry on the first run afterwards.

⚠️ **The sixth violation (§2.4's `lb`/`rb` imbalance) is expected to SURVIVE the migration**, because it is a source-content asymmetry faithfully transcribed by a 1:1 escaper — a re-extract reproduces it. **So the allowlist is not certain to be empty; it is likely to shrink from six to one.** Design it, do not necessarily populate it.

**The allowlist reports its own staleness:** an entry matching no current violation is reported, not silently ignored. Without that, the allowlist only grows, and a fixed defect leaves an entry that would mask its recurrence.

### 6.1 CI wiring — `test.yml`, and NOT `validate.yml`

**[measured-here]** `validate.yml`'s path filter is `books/**/status.json`, `templates/**`, `schemas/**`, `scripts/validate-status.js`, `books/**/05-publication/**`, `tools/cnxml-render*.js`. **None of the marker-bearing trees are in that list** — a check added there would never run on the content it checks. ## 7. Testing

Designed against two of this project's recorded failures: *a green gate suite is evidence about the code and none at all about the suite*, and *a whole verification stack can be green and blind in the same direction*.

### 7.1 Rules module — `server/__tests__/markerIntegrity.test.js`

Every rule gets a **paired control that must not fire**:

| Rule | Positive | Control that must stay silent |
|---|---|---|
| 1 | `[[i: vatns]]` | `[[i:vatns]]` |
| 1a | — | **a complete nested construct** (§2.2) — must not read as malformed |
| 1b | `[[i:x]]]]` (unbalanced) → block | the same complete nested construct → silent |
| 2 | `[[MATH:4]]` → `[[MATH:5]]` → **block** (atomic mutation, §4.2) | `[[sub:2]]` → `[[sub:tveir]]` → silent (structural content) |
| 2 | drop `[[sub:2]]` → block | reword *inside* `[[sub:…]]` → silent |
| 2 | duplicate `[[MATH:1]]` → block | — |
| 3 | `[[zz:x]]` → warn | all 17 known types → silent |
| 4 | `[[lb:]]x` → warn | `[[lb:]]x[[rb:]]` → silent |

The nesting control matters most: it is the case a naive implementation gets wrong, and it fails by flagging *correct* chemistry.

### 7.2 Mapping — `server/__tests__/segmentValidationMarkers.test.js`

Structural drops land in `blocked`, presentational in `warnings`. Plus a regression control: an edit touching no markers returns exactly what it returned before this feature, so the existing codes are untouched.

### 7.3 The gate's self-test — `server/__tests__/checkMarkerIntegrityGate.test.js`

**This test calls the script.** Four cases against a temp fixture tree:

1. planted violation → **non-zero exit**, violation named in output
2. same violation, allowlisted → **exit 0**
3. same violation **moved to another segment in the same file** → **non-zero**
4. clean tree → **exit 0**

Case 3 is the one that would otherwise rot: a per-file allowlist passes 1, 2 and 4 and is still wrong.

### 7.4 Real-corpus regression fixtures

The known defects become fixtures, being the only inputs known to occur in practice: the 5 malformed markers, the ch12 `lb`/`rb` imbalance, and the genuine complete nested construct from §2.2 lifted verbatim from chemistry. If the rules do not flag the first two, or *do* flag the third, the rules are wrong.

### 7.5 One E2E with real user input

A Playwright spec that types a space into a marker and asserts the save is refused with the right message. Every other test here checks a property of the code; this one checks what an editor actually does.

### 7.6 Cross-implementation consistency — what makes §5.1's duplication safe

One test feeds a shared fixture to **both** `countBracketMarkers` (`tools/`) and the new scanner (`server/`) and asserts **identical counts for every shared type**. Duplicated logic is acceptable only because this test exists; without it, §5.1 is a drift generator rather than a decision.

⚠️ It must also assert both read the **same** `marker-types.json`, or the test passes while the two sides disagree about which types exist.

## 10. Risks

- **A rule that is too aggressive blocks propagation as well as saves** (§2.5). Mitigated by tiering: only atomic and structural drops block, and presentational — the class most likely to change legitimately between languages — only warns.
- **The nesting trap (§2.2) is silent when got wrong** — it flags correct content rather than missing bad content, so it would surface as editor complaints, not as a red test. §7.1's nesting control is the guard.
- **The allowlist becomes a mute button** if granularity or staleness reporting is dropped. §7.3 case 3 and §6's staleness report are the guards, and both are testable.
