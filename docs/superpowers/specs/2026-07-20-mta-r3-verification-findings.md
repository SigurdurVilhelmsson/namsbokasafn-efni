### [blocking] `discuss` is an OPEN disagreement, not a closed decision — accepting over it forks the two definitions of "done" and lets any editor end-run four-eyes
**Detail:** rejected and discuss are not equivalent. `completeModuleReview` (segmentEditorService.js:716: `allReviewed = counts.pending === 0 && counts.discuss === 0`) treats a discuss row as OUTSTANDING WORK that blocks the review session. Acceptance touches nothing on the edit side (approveEdit/rejectEdit/markForDiscussion never call into acceptanceService; only saveSegmentEdit and propagationService supersede acceptances), so the discuss row survives. Result: `getEditorialProgress`/`getReviewedSegmentsByModule` (:1363-1380, approved ∪ active-acceptance) count the module COMPLETE while `completeModuleReview` refuses to complete it, and `getModuleStats` reports `discuss: 1` and `accepted: 1` for the same segment — the stats bar renders both chips side by side. Editorially worse: the acceptance is a single-step action open to ANY editor with book access (spec §2 decision 1, route gate `requireBookAccess`), so an editor who is not party to the discussion can unilaterally close a flagged disagreement, and the person who raised it is never notified (approve/reject notifications are unbuilt — throughput-roadmap Unit 5). A frontend-only gate is decorative: `acceptanceService.acceptSegment` (:83-93) blocks only pending / approved-unapplied, so the API accepts a discuss segment regardless. RECOMMENDATION: exclude `discuss` from the accept affordance AND add a backend block (new coded error) so client and server agree. These segments genuinely are unhandled — the outstanding work is the discussion, and exits already exist (returnEditToPending → reject, or editor revises).
**Scenario:** Editor A flags a term choice; HE marks the edit 'discuss'. Editor B (uninvolved) opens the module, sees the segment, hits "Staðfesta MT". ### [blocking] SUPERSEDED-as-latest is always a MASKED rejected/discuss row — and it is the bypass that makes any discuss block useless
**Detail:** Reachability proof: `superseded` has exactly two producers. (a) apply-time losers (segmentEditorService.js:1063) — the winner is `pickLatest(created_at,id)` among approved rows, so a loser is by construction OLDER and can never be `edits[0]`. (b) the save-time sweep of the editor's OWN stale discuss/rejected rows (:138 and :175) — that sweep is followed by a NEWER pending row, so it only surfaces as `edits[0]` when that pending row is subsequently DELETED, which happens in exactly one place: the withdraw branch (:109-116). The client's own comment says so (:791 "Superseded edit (latest, e.g. after a withdraw)"). Therefore `edits[0].status === 'superseded'` means "there was a rejected or discuss row here, the editor revised, then withdrew the revision" — NOT the register's "a newer edit exists". Two consequences: (i) the chip the editor reads is UI.editStatus.superseded = 'Leyst úr gildi' ('resolved/void'), which asserts the matter is settled when it may be an unresolved discussion — the UI actively misleads at the moment of attestation; (ii) blocking discuss while allowing superseded is trivially bypassable with no privilege: mark discuss → editor edits → editor withdraws → status is now superseded → accept button appears. Any gate must therefore look at the segment's EDIT HISTORY, not at `edits[0].status`, and the server must expose that judgment (see recommendedApproach) because status alone cannot distinguish ex-rejected from ex-discuss client-side.
**Scenario:** HE marks a segment 'discuss' ('is this the right term?'). The editor opens the pane, types a revision (the discuss row flips to 'superseded'), then reverts the textarea and saves — the withdraw branch DELETEs the pending row. `edits[0]` is now the superseded ex-discuss row rendering the chip "Leyst úr gildi". Under the register's fix the accept button appears; the editor reads "resolved" and attests. The open question is buried under a green attestation with no trace in the sidecar.

### [important] Sweeping contested rows into the Ctrl+Shift+Enter accept-and-advance stream is the wrong half of the register
**Detail:** The register instructs "make isUnhandled/nextUnhandledAfter treat a non-active-edit segment as unhandled". The keyboard flow (acceptAtCursor :1030-1044, nextUnhandledAfter :961-969) is deliberately a rapid-fire rhythm — read, keypress, read, keypress — designed for virgin MT rows where the only judgment is "is this sentence fine". Dropping segments carrying a head editor's rejection or a buried discussion into that same stream is precisely where blind attestation happens: the two-press safety (press 1 parks the cursor, press 2 accepts) gives no pause because both presses are in the same motor loop, and the contextual chip scrolls past at speed. Contested attestation deserves ceremony — a deliberate click with the history visible. The Óyfirfarnir FACET, by contrast, SHOULD include these rows (they are the true unreviewed backlog, and the facet already omits `hasTranslation`, differing from isUnhandled). So the two predicates should intentionally diverge and be NAMED rather than duplicated a fifth time inline.

### [important] The gate is being duplicated client-side for the fifth time — that duplication IS the root cause of MTA-R3
**Detail:** "Unhandled"/accept-eligibility is already encoded five times (isUnhandled :952, the Óyfirfarnir facet :689-701, renderProgress :584-594, the branch control flow :876-887, and the backend SQL in acceptanceService.js:83-93), and two of them already disagree about `hasTranslation`. Worse, a client-only gate cannot enforce the discuss/provenance blocks at all, since POST /accept is directly reachable.
**Scenario:** A later change tightens the backend (e.g. blocking discuss) but not the client, or vice versa; the button appears and 409s, or the button is hidden while a scripted/replayed POST still succeeds. Exactly the shape of the divergence being fixed now.

**Recommended approach:** REJECT the register's MTA-R3 fix as written and rescope it. The spec (docs/superpowers/specs/2026-07-19-mt-acceptance-design.md) still stands; the fast-follow design does not. The core error is that the register treats {rejected, discuss, superseded} as one equivalence class keyed on `edits[0].status`, when they are three different editorial situations and the state that actually decides honesty is the BASELINE'S PROVENANCE plus whether an open question exists.

Rescoped design, in dependency order:

1. FIRST, unconditionally: lift acceptance rendering out of `else if (acceptance)`. The "Staðfest" chip, the `accepted-row` tint and the "Afturkalla staðfestingu" revoke button must render whenever an active acceptance exists, regardless of `latestEdit`. This is a bug in the SHIPPED code, not only in the proposed fix (the coexistence state is already reachable today per the code map's Q4 walkthrough: pending edit → HE rejects → POST /accept via API succeeds), and it must land even if nothing else does. Rows with both get a compound chip ("Staðfest" + the history chip).

2. Move eligibility to the SERVER as the single source of truth. Have the module GET add a derived per-segment field (e.g. `accept: {eligible: bool, reason: 'rejected'|'discuss-open'|'not-mt-baseline'|…}`) computed by the same acceptanceService predicate the POST enforces. The client renders from that field and stops re-deriving the rule. This kills the divergence class rather than adding a sixth copy.

3. Tighten the backend predicate, with tests:
   - BLOCK when an unresolved discussion exists on the segment — including the buried case where the discuss row was swept to 'superseded' and its successor withdrawn. Because status alone can't distinguish that, the check must walk the segment's edit history (and/or the exit paths must explicitly resolve a discuss row rather than sweeping it).
   - BLOCK when the current baseline is not the machine translation — compare `seg.is` against the `02-mt-output` bytes for that segment (the module paths are already resolved in segmentParser.getModulePaths). This is the honest predicate; it simultaneously covers hazard 4, the hand-fixed-faithful case, and the restore edge, WITHOUT reddening acceptanceService.test.js:472 (whose acceptance is over bytes that do equal the file baseline — verify against the fixture and, if it does trip, adjust the assertion deliberately with the lead rather than weakening the rule). If a non-MT baseline should still be attestable, do it as a distinct, distinctly-labelled action — never under "Staðfesta MT".
   - KEEP allowing the plain rejected case (acceptanceService.test.js:179 must stay green): a rejection is a closed decision by the authority, MT stands, and acceptance is the only exit from a segment that is otherwise permanently unreviewable.

4. Frontend, driven by (2): show the button in the edit branch only when `accept.eligible`, alongside a VISIBLE Icelandic hint stating why the row is contested, plus a confirm dialog naming the rejecting reviewer and date. Include contested rows in the "Óyfirfarnir" facet (true backlog) but EXCLUDE them from `nextUnhandledAfter`/`acceptAtCursor` — split the predicate into two named functions (`isUnattested` for facet/progress, `isQuickAcceptable` for the keyboard stream) and delete the inline duplicates at :689-701, :584-594, :876-887 in favour of them. Reconcile the existing `hasTranslation` asymmetry while there.

5. Tests: no static pin in acceptanceUiPins.test.js references any branch condition, so restructuring breaks zero pins provided the labels, class names and handler names survive verbatim. Add (a) service tests for the discuss block and the non-MT-baseline block; (b) an e2e in server/e2e/acceptance.spec.js that rejects an edit, asserts .btn-accept appears on that row, accepts, then asserts BOTH the Staðfest chip and the revoke button render on a row that still shows "Hafnað"; (c) an e2e asserting the keyboard cursor SKIPS a contested row. Watch the relative `.btn-accept` counts at acceptance.spec.js:44/61 — they will move, and m68664 is a shared mutable fixture used by six other specs.

6. Lead decision to surface before coding: single-step accept (spec §2 decision 1) means the editor whose edit was just rejected can themselves attest that the MT is fine — recording, as durable research provenance, an agreement they demonstrably do not hold. Not a code bug, and blocking self-accept would recreate the deadlock; but the register's fix makes this the ROUTINE path, so the lead should decide whether the confirm copy is sufficient mitigation or whether post-rejection attestation should belong to the rejecting head editor. Fold into register MTA-R1's release note to ritstjórn alongside the rising-completion-numbers comms.
