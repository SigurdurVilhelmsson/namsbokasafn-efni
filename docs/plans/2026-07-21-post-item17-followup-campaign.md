  - **(a) Uncaught `error` → process exit. MEASURED, four scenarios, and the boundary is sharper than "a missing file".** The handler's `existsSync`/`statSync` guard does not close the window because `archive.file()` builds a **lazy** read stream.     | Scenario | Outcome | Repeatability |
    |---|---|---|
    | unlink **immediately** after `.file()` (archiver's stat fails) | `warning ENOENT`, `finalize()` **resolves**, exit 0 — process survives | 6/6 |
    | unlink one tick later, **after** the stat (`setImmediate`) | **UNCAUGHT `ENOENT` → exit 1** | ⚠️ **1 of 6** — a genuine race with a narrow window |
    | `chmod 000` after `.file()` — stat succeeds, read denied | **UNCAUGHT `EACCES` → exit 1** | 6/6 — **the deterministic reproducer** |
    | an appended stream that errors mid-read | **UNCAUGHT → exit 1** | 3/3 |

    In every crashing case the handler's `try/catch` around `await archive.finalize()` **does not fire**: `_modulePipe` registers `_onModuleError` on the module *before* `finalize()` installs its reject listener, so `_onModuleError`'s `this.emit('error', err)` throws out of the module's `emit` and the rejection path never runs. ⚠️ **The first row is exactly the measurement §C19's fact (b) reports** — which is why both are true and why (b) must be read as scoped to that condition. ⚠️ **Use the `chmod` row to reproduce, not the unlink row** — unlink-after-stat crashed only 1 run in 6, so a fix "verified" against it will look green ~83% of the time on broken code. ⚠️ **Not hypothetical**: "Vista + Birta" rewrites `05-publication/` on the same box the download reads from, so a re-render concurrent with a download is a real trigger, not a contrived one.

  - **(c) The C19 test cannot see either.** It settles on the response stream's `end` or on `res.json`, so a mid-stream failure is outside what it observes. **Do not read C19's green as coverage of this.** A fix needs its own harness — one that injects a read failure mid-archive, which likely means making the file-enumeration seam injectable.
  - **🔴 THE OBVIOUS ONE-LINE FIX IS A TRAP — MEASURED 4/4, and this is the most useful thing in this entry.** Adding just `archive.on('error', …)` — the fix anyone would reach for — **does not fix it; it converts a crash into a hang.** With a listener attached and the deterministic `chmod` trigger: the listener fires with `EACCES`, and then **`finalize()` never settles** (still pending at 3 s) and **`res` is never ended**. So the process survives and the editor's browser instead holds an open chunked download that never completes and never errors, while the handler's promise and the `Archiver` leak for the process lifetime. A "fix" validated only by *"the server stopped crashing"* will ship exactly this.
  - **Shape of the fix (not prescribed — decide when taken):** the `error` handler must **also end the response** (destroy `res`) and stop waiting on `finalize()`, plus `res.on('close')` → `archive.abort()` for (b). ⚠️ A second constraint makes the reporting non-trivial: once `archive.pipe(res)` has written a byte, `res.headersSent` is **true** and the existing catch block's `res.status(500).json(...)` is already unreachable — so the handler cannot report a mid-stream failure to the client as JSON, only truncate. Whatever ships must decide what a half-written ZIP looks like to the editor. **Verify against the `chmod` reproducer and assert on *both* — no crash AND the response settles.** *[severity: robustness/availability — process-level · blocks: nothing]*
