# Editorial-Workflow Review — namsbokasafn-efni Editorial Server

**Date:** 2026-07-11
**Lens:** seasoned translator/editor — professional translation-shop practice (review states, four-eyes integrity, TM/terminology lifecycle, traceability, rollback safety, onboarding) applied as a benchmark against this project's editorial server.
**Companion report:** [`docs/audit/2026-07-11-server-code-review.md`](2026-07-11-server-code-review.md) carries the full 37-finding adversarially-verified code review. This report does not re-enumerate that list; where a code finding is the mechanism behind a process observation here, it is cited by number and file:line, not reproduced.

### Audience boundary

The people who run this system are chemistry teachers acting as editors and head-editors, not professional translators, and there are roughly five of them. Every recommendation in this report is a **process** recommendation — about state machines, gates, audit trails, recovery paths, and documentation accuracy — never a vocabulary recommendation. Nothing here proposes introducing CAT-tool/translation-shop jargon, added save-time friction, or extra process ceremony into the editor-facing UI. Where the system's own deliberate simplifications for this audience are sound — advisory-not-blocking QA, role-based (not person-based) self-approval on a five-person team, hiding the 8-stage pipeline vocabulary from the editor role — this review says so plainly rather than treating professional-shop norms as a universal target the project should be graded against.

### Method

1. **Documented-model construction** — read `docs/`, `.claude/skills/`, `CLAUDE.md`, `README.md` only (no source code) to build a ground-truth model of the workflow *as documented*: pipeline stages, the segment/edit state machine, the role×action matrix, gates, artifacts, and the MTPE (machine-translation post-editing) reframe. Every documentation tension the corpus itself contains was catalogued rather than silently resolved.
2. **Docs↔code cross-walk** — every documented gate, state transition, and role rule was checked against the actual `server/` and `tools/` source, each verdict backed by a specific `file:line` citation.
3. **Live persona walkthrough** — a throwaway server (fresh `pipeline-output/review-sessions.db`, 38 migrations, port 3456) seeded with a dedicated `__e2e-fixture__` book, driven live through Editor, Head-editor, and Admin personas via Playwright plus direct `curl`/DB reads, producing 24 screenshots and a full mutating pass (apply → version history → restore → edit-again → rebuild → localization round trip).
4. **QA checklist §0–§5 absorption** — every still-open row of the 2026-06-10 remediation QA checklist re-walked live against the same server.
5. **Eight-dimension professional-practice benchmark** — a judgment synthesis over all of the above, plus a 41-finding adversarial code-review fan-out that was itself independently re-verified in a second pass (31 KEEP / 6 DOWNGRADE / 4 DROP).

Every claim below is tagged by its evidence basis where that matters: **LIVE** (observed against the running throwaway server this session), **CODE-READ** (confirmed by reading source, not exercised live), or **document-comparison** (a claim about what the docs themselves say). Known data-starvation states (thin TM, thin concordance corpus — the project has roughly three faithful modules total) are stated as the known, already-documented state, never dressed up as a fresh live finding.

## §1 The documented workflow

*(Condensed from this review's documented-workflow modeling phase — read `docs/`, `.claude/skills/`, `CLAUDE.md`, and `README.md` only, per the method in `docs/plans/2026-07-10-server-editor-two-perspective-review-plan.md`.)*

**Pipeline stages.** CLAUDE.md documents eight `status.json` stages, each with a specific tool: `extraction` (`cnxml-extract.js`, CNXML → EN segments), `mtReady` (legacy protect/split step, now archived), `mtOutput` (`api-translate.js` against the Málstaður API), `linguisticReview` (segment editor / `applyApprovedEdits()` → `03-faithful-translation/`), `tmCreated` (`generate-tm.js`, in-house TMX from aligned segment pairs), `injection` (`cnxml-inject.js` → `03-translated/{track}/`), `rendering` (`cnxml-render.js` → `05-publication/{track}/`), and `publication` (HEAD_EDITOR-gated publish action). The documentation corpus actually contains **two incompatible accounts** of the MT and TM-creation steps — an automated one (Málstaður API + in-house TMX generation) and a legacy manual one (hand-upload to malstadur.is, hand-built TM via Matecat Align) — carried in different documents with no cross-reference between them; the model follows the automated account as current, per the dated, lead-approved retirement decision in the June throughput roadmap. §2 below resolves this against actual code.

**Segment/edit state machine.** The corpus describes five loosely-coupled state machines rather than one: (1) the Pass-1 segment edit lifecycle (`segment_edits.status`: MT-draft → `pending` → `approved`/`rejected`/`discuss`, with the whole module's approved edits collapsing to `applied` via `applyApprovedEdits()`; a published segment can be revised forward via "Breyta aftur" (edit-again), but `unapproveEdit` is a one-way lock once `applied_at` is set); (2) the `module_reviews` submission wrapper, a separate table an editor advances by clicking "Submit module for review"; (3) per-module, per-track publication progression (`not-published → mt-preview → faithful → localized`, each track replacing the previous on the live site, no documented "unpublish"); (4) the Pass-2 localization edit lifecycle, which is contingent on a per-book toggle (`enforce_localization_review`) the Pass-2 editorial docs never mention; and (5) content-restore, a parallel *file-level* undo mechanism (`contentVersionService`) that sits alongside, not inside, the row-level edit machinery.

**Roles × actions.** Three effective roles — editor, head-editor, admin (a fourth, `contributor`, is named in README but is a documentation fossil — see §2). The one unambiguous rule the corpus states on approval integrity: Pass-2's four-eyes gate "mirrors Pass 1 (head-editor-only approve, self-approval permitted)" — the gate is **role-based, not person-based**. No document states whether this was a deliberate call or an overlooked gap.

**Gates.** Approval gates (all HUMAN, head-editor-or-above): Pass-1 approve/reject/discuss, the module-submission wrapper, Pass-2 approve/reject (conditional on the toggle), track publication, glossary term approve/dispute-resolve, mined-term promotion. QA gates are **deliberately, explicitly advisory** across the board — terminology consistency (segment- and module-level), EN-residue, and number-consistency all surface as non-blocking toasts on save; spellcheck (GreynirCorrect) is kept off the save path entirely as an on-demand pull, because it depends on an external sidecar. The roadmap states this design choice in its own words: "warnings, not blocks — terminology stays advisory in force but becomes impossible to miss." Exactly **one** gate is genuinely hard: structural markers (`[[MATH:N]]`, cross-refs, links) are blocked on save; only unbalanced formatting is a warning. Access gates: chapter-assignment enforcement and book-scoped head-editor authorization, both toggleable per book and both documented as off/fail-open by default.

**Artifacts.** The `01-source/` → `02-for-mt/`/`02-structure/` → `02-mt-output/` → `03-faithful-translation/` → `03-translated/{track}/` → `05-publication/{track}/` chain, with `tm/` generated from faithful segments and the glossary split across a hand-maintained CSV and a DB-backed JSON export (resolved in §2).

**The MTPE reframe.** The June 2026 throughput roadmap reframes the whole project as **machine-translation post-editing**, not from-scratch human translation: every segment arrives at Pass 1 already carrying a Málstaður MT draft, primed by the approved glossary. Three consequences follow: fuzzy TM matching is dropped *permanently* (a fuzzy match is a stale near-miss against an MT draft that's already a fresh, correctly-targeted translation); exact-match leverage exists to deduplicate review effort, not to pre-fill text; and the **glossary, not the TMX, is the asset that improves future MT quality**, because it's what's sent to Málstaður on every request. The roadmap names the corresponding reviewer risk this motivates: "'fluent-but-wrong' is the signature MTPE reviewer failure mode — smooth MT output charms reviewers past accuracy errors, omissions, and number slips." This framing exists in exactly one document and has not been back-propagated into the editor-facing process docs (§2, §5 dimension 8).

## §2 Docs ↔ code drift

**§H coverage tally (as computed by the drift catalog, every documented gate/state/artifact claim cross-walked):** **45 MATCH / 11 DOCS-AHEAD / 9 CODE-AHEAD / 1 DRIFT (minor) / 2 UNDETERMINED.** The two UNDETERMINED rows are infrastructure facts outside this repo's reach: whether `GREYNIR_URL` is actually set in production, and whether a reader genuinely sees a correctly-assembled "mixed" chapter page when only some of its modules have been promoted past mt-preview (that assembly logic lives in the sister repo, namsbokasafn-vefur).

### Headline drifts

**1. The "workflow trap" is fixed on the read side, but the fix is undocumented, and the thing it was supposed to replace was never actually removed.** `server/services/dashboardReadModel.js` reads exclusively from `segment_edits` — never from the `module_reviews` wrapper — so an editor's saved edit is visible to admin/head-editor dashboards immediately, with no "Submit module for review" click required. This is real, shipped code (a real commit history and its own test file), wired into the live dashboard and the global-pending list. But it is **completely undocumented** — `grep -n "dashboardReadModel"` on CLAUDE.md and README.md returns zero hits. Meanwhile the flag that was supposed to formalize this fix and retire the old submit button — `ENABLE_DIRECT_QUEUE` — **does not exist anywhere in code**; it appears only in two planning documents. The submit button (`#btn-submit`) is still live, unconditional, and wired to its original endpoint. Net effect: a hybrid state no single document describes — basic pending-work visibility no longer requires submitting, but the *structured*, SLA-trackable review queue (`GET /reviews`) still only groups edits that were submitted, and stays empty otherwise. A new head-editor reading only CLAUDE.md would not know the counter fix already exists and might re-propose or re-build it; an editor clicking "Submit" today is doing something narrower than the button's own label implies.

**2. `npm run update-status <book> <chapter> <stage> <status>` — documented in CLAUDE.md's Commands table and its "Status Updates" section as the way to advance chapter status — does not exist as an npm script.** `package.json`'s `scripts` block has no `update-status` entry; the implementing script was moved to `scripts/archived/update-status.js` when the legacy review system was archived. A user following CLAUDE.md's own literal instructions gets `npm error Missing script: "update-status"`. Status advancement is now automatic (`pipelineService.advanceChapterStatus`, called from the pipeline runner and from `applyApprovedEdits`) — except for the `tmCreated` stage, which nothing advances anymore, manually or automatically; it is now an orphaned field in the schema.

**3. The "`tm/` is empty in every book" claim is stale.** The June roadmap's production-state snapshot (dated 2026-06-12) is now inaccurate for `efnafraedi-2e`, which holds a real, if small, 3-translation-unit TMX (`efnafraedi-2e-2026-06-13.tmx`, generated from the one faithful module that existed at the time). The other four books genuinely have no `tm/` directory at all. The underlying *mechanism* the roadmap describes — `tmService.scheduleTmRegen`, fired from `applyApprovedEdits` after every write, debounced 5 seconds, spawning `generate-tm.js` — is real and matches the documentation exactly (this is a MATCH); it is specifically the roadmap's literal snapshot sentence that a reader would now be wrong to trust at face value.

### Further drift, both directions

- **DOCS-AHEAD, self-inflicted authority problem:** `docs/workflow/master-pipeline.md` self-declares itself *"the authoritative reference... all other workflow documentation should be consistent with this document,"* yet describes the retired manual malstadur.is-web-UI + Matecat-Align pipeline as current. `docs/workflow/mt-process.md` and `.claude/skills/workflow-status.md` are built entirely on the same retired account. `tools/archived/` confirms the automated `api-translate.js` + `generate-tm.js` path is what's actually live; the legacy tools (`protect-segments-for-mt.js`, `prepare-for-align.js`, `unprotect-segments.js`, `restore-segments-from-mt.js`) are archived, not deleted, but genuinely inert.
- **DOCS-AHEAD, terminology CSV is disconnected from live MT quality:** `docs/editorial/terminology.md` instructs editors to maintain `glossary/terminology-en-is.csv` and calls it "the authoritative source for approved terminology." `tools/api-translate.js` reads **only** `glossary-unified.json` — a separate, DB-backed export. On disk, the CSV is dated 2026-01-02 (stale); the JSON is dated 2026-03-11 (live). An editor diligently following the documented instruction has zero effect on translation quality through that channel (developed further in §5 dimension 3).
- **DOCS-AHEAD, an undocumented directory has its own detailed, unimplemented process description:** `books/efnafraedi-2e/04-localization/README.md` describes a two-stage Pass-2 workflow (edit in `04-localization/`, then "promote" to `04-localized-content/`). No code anywhere references `04-localization` at all; the real, live save route writes directly to `04-localized-content/` in one step.
- **DOCS-AHEAD, an auto-triggering skill teaches the wrong review model:** `.claude/skills/review-protocol.md` — which auto-triggers per CLAUDE.md's own skill table on the topic "discussing reviews or approvals" — documents an entirely different, retired `files.json`/Word-Track-Changes review model with no connection to the live segment-editor system. This is the single most consequential documentation drift for onboarding specifically (§5 dimension 8), because it is not a stale footnote — it is a document the tooling itself actively surfaces at the moment someone asks how review works.
- **DOCS-AHEAD, a role that was deliberately removed is still documented:** README's five-role Auth line and `master-pipeline.md`'s glossary-dispute "contributor" actor both describe a role merged into `editor` by a dated migration (`023-merge-contributor-role.js`, comment: *"too granular for a ~5 person team"*). `viewer` is real and load-bearing (default role for auto-created users) but is nowhere described in prose.
- **CODE-AHEAD, an open design question turns out to already be answered in code:** the 2026-05-10 audit's Open Question 1 — "should admin approval override head-editor decisions; does the data model need an 'override' field?" — is resolved architecturally: admin simply bypasses the per-book ownership check one level up in the same middleware (`requireHeadEditorFor`), no override field needed. No document states this resolution.
- **CODE-AHEAD, publication status is richer than any one document describes:** a nested schema (`publicationStatus` → per-track `stageStatus` children) *and* a fully independent filesystem-scan-based read path (`publicationService.getPublicationStatus` derives "what's actually live" by scanning `05-publication/{track}/` at request time, not from the stored status at all) coexist — neither CLAUDE.md's flat single field nor `master-pipeline.md`'s three top-level flags describes this.
- **DRIFT (minor):** the module-level terminology report is documented as firing "on submit," but actually fires whenever a head-editor opens the module — functionally earlier, not worse, but a real wording mismatch (confirmed live in §3).

## §3 Live walkthrough findings

Server: throwaway `pipeline-output/review-sessions.db`, 38 migrations, `__e2e-fixture__` book (chapter 1, modules `m68663`/`m68664`). Driven via `server/e2e/walk.spec.js` (Playwright) plus direct `curl`/DB reads. **24 screenshots** captured across the four personas (`editor-01..08`, `head-editor-01..07`, `admin-01..06`, `apply-01..02`, `loc-pass2-01`), stored alongside this review's working artifacts.

### Editor persona (LIVE)

- **"Today" honesty gap (minor):** a fresh login with zero prior work shows a celebratory "no tasks today, you're all caught up" message that does not distinguish *never been assigned anything* from *cleared a real queue*. Not a functional bug — a wording nuance a brand-new editor could misread.
- Deep links work exactly as coded; the MTPE editing loop (term-lookup box, concordance search, marker overlay rendering a `[[i:...]]` bracket marker live, save) all worked without incident. Save-state feedback is clear and honest: "Allar breytingar vistaðar" ("All changes saved").
- **The submit-button trap, live-confirmed:** the "Submit module for review" button is still visible and unconditional, confirming §2's finding that the flag meant to retire it was never built. The editor in this walkthrough never clicked it — whether the work was invisible anyway is answered by the Head-editor/Admin personas below: it was not.

### Head-editor persona (LIVE)

- **§2's headline finding, directly reproduced:** `module_reviews` was empirically **empty (0 rows) for the entire session**, yet the editor's unsubmitted edit was visible and actionable to the head-editor throughout, and correctly reflected in the admin activity feed. The *structured* review-queue endpoint (`GET /api/segment-editor/reviews`) returned an empty list the whole time, confirming the other half: it really does stay submit-gated even while basic visibility does not.
- Self-approval, live-confirmed: the head-editor edited a segment under its own identity and approved its own work with no obstacle in the UI — matching the documented, deliberate design.
- **Bug (a) — a raw SQL error reaches a head-editor's screen.** DB trace on `__e2e-fixture__`:
  ```
  id=4  m68664:abstract-item:abstract-item-1  status=discuss   editor=test-head-editor
  id=5  m68664:abstract-item:abstract-item-1  status=pending   editor=test-head-editor
  ```
  The same editor saved a second revision of a segment that already carried a stranded `discuss` row from an earlier revision, then clicked "discuss" again on the new pending edit. The server responded with HTTP 400 and a **raw SQLite constraint message surfaced verbatim to the user via a browser `alert()`**: *"Villa: UNIQUE constraint failed: segment_edits.book, segment_edits.module_id, segment_edits.segment_id, segment_edits.status, segment_edits.editor_id."* Root cause, confirmed by reading the code: migration 008's unique index on `(book, module_id, segment_id, status, editor_id)`, combined with `markForDiscussion` having no `try`/`catch` around the constraint violation, combined with the fact that no code path anywhere moves a `segment_edits` row *out of* `discuss` or `rejected` status once set — a fresh save on a segment with a stale `discuss` row inserts a new row rather than resolving the old one, leaving the original permanently stranded. This is real, it is reachable through ordinary use (revise a segment that was previously discussed, discuss it again), and it is head-editor-facing, not an admin-only edge case.
- The terminology/QA report panel loads on module-open, confirming §2's "fires earlier than documented, not later" drift.

### Admin persona (LIVE, cross-checked against raw API/DB state, not eyeballed)

- **Dashboard truthfulness:** the `needsAttention` tile counts (`pendingReviews`, `blockedIssues`, `unassignedWork`, `overdueCount`) were checked against the live `GET /api/status/dashboard` JSON and the underlying `segment_edits` rows directly — no discrepancy found. `discuss` is counted alongside `pending` in "awaiting decision," which is sensible given that `discuss` has no resolution path of its own (bug (a) above). The activity feed independently reproduced this session's exact action sequence, correctly ordered, correctly attributed, in Icelandic.
- **Terminology governance, full loop, live end to end:** created a term via the terminology-manager UI modal → approved it as head-editor → re-exported via the "Export CSV" button — all three steps confirmed working with real DB/response evidence. Deliberately **not** exercised live (to avoid mutating a real book's tracked file), and confirmed instead by code read: the disk-writing `glossary-unified.json` export — the file `api-translate.js` actually consumes for MT priming — is a separate, CLI/cron-only script with **no route or scheduled-job wiring found anywhere in the repo**. The UI's "Export CSV" button and the MT-priming JSON export are two different code paths; only the first is reachable from the editor UI at all.
- Assignments dashboard renders live, real (not placeholder) data — a genuine 1.2% chapter-progress figure, correct enforcement-toggle state.

### Cross-cutting (LIVE)

- **Concurrent-edit conflict:** two distinct editor identities saving the same segment produced a clean `200`/`409` split, with the losing save receiving a specific, named-actor, actionable Icelandic message ("Another reviewer (test-editor) has changed this segment. Reload to see the latest version.") rather than a generic error.
- **Spellcheck with the Greynir sidecar absent** (as in production, where `GREYNIR_URL` is unset in this shell): a real request returned a clean `200 {enabled:false, segments:[]}` — graceful degradation confirmed live, not just architecturally plausible from a code read.
- **Assignment enforcement — a real, narrow, non-exploitable gap found by contrast-testing:** with `enforce_assignments` ON, a seeded identity (one with a `users` DB row) correctly got `403`; a deliberately unseeded identity (no `users` row) got `200` — **enforcement silently skipped**. Root cause: `requireBookAccess()`'s enforcement branch only runs `if (dbUser)`; a missing row falls through to allowed rather than denied — the opposite of the fail-closed posture the same code takes one branch later for a *missing table*. Fairly caveated: this is **not reachable through the real Entra OAuth login path** — `auth.js`'s OAuth callback auto-creates the `users` row at login time, before any session issues, so a normally-authenticated user always has a row by the time they hold a valid cookie. The gap would only bite if a `users` row were deleted after a session was already issued and still valid — a real but narrow, untested boundary condition, not a routine exploit path.

### Mutating pass (LIVE — apply, version history, restore, edit-again, rebuild, localization)

- Pass-1 apply created the fixture's faithful file for the first time, exactly as expected.
- **Version-numbering nuance, discovered live and worth stating precisely:** a version row is a snapshot of the content that existed *before* a write, not the result of that write. Version 1 was the pre-edit MT-derived baseline; version 2 (carrying the actual edit) was created as a side effect of the *next* restore call. Practical consequence: a head-editor opening "Saga útgáfa" and intuitively picking the lowest-numbered version to restore ("version 1 = my first change") would actually discard the most recent approved edit, not recover an old one. Whether the restore modal's own UI already disambiguates this with per-version diffs wasn't confirmed at pixel resolution this session (the screenshot was too small to read reliably) — flagged as worth a two-minute follow-up check, not asserted as a UI bug.
- **Restore round trip, both directions, confirmed clean and byte-correct on disk:** restored back to version 1, then forward again to version 2, file contents verified correct after each step. `version_restored` activity-log entries carried correct actor, Icelandic description, and metadata for both directions, no gaps.
- Edit-again on an already-applied segment worked exactly as documented (forward-only, old row untouched).
- **Rebuild affordance, both halves confirmed:** deliberately deleting the on-disk faithful file correctly flipped `can_rebuild:true`; re-applying recreated the file on disk with the edit-again content — a real, working recovery path, not just a documented intention.
- **Bug (b) — TM auto-regeneration silently WARN-skips for a book slug starting with an underscore.** The apply-triggered TM regeneration call site fires exactly as documented on every apply, but `tools/generate-tm.js --book __e2e-fixture__` exited non-zero: `tools/lib/parseArgs.js`'s `BOOK_SLUG_PATTERN` requires the slug to *start* with an alphanumeric character, and `__e2e-fixture__` starts with `_`. The failure is logged only as a server-side `pino` WARN — invisible to any human, absent from the activity-log timeline, with the apply's own HTTP response still reporting unqualified `success:true`. **Scope, precisely: this is fixture-only.** All five real book slugs (`efnafraedi-2e`, `liffraedi-2e`, `orverufraedi`, `lifraen-efnafraedi`, `edlisfraedi-2e`) start alphanumeric and are unaffected — this cannot happen to a real book today. It is best read as a robustness/observability finding (a silent-failure path exists in the TM pipeline, and the validator's own error message is imprecise about which character it's rejecting), not a production defect.
- The Pass-2 localization round trip, with `enforce_localization_review` toggled ON for the fixture, completed cleanly end to end: editor's save correctly queued rather than direct-saved, head-editor's approval wrote the real `04-localized-content/` file, toggle cleanly reset afterward.

## §5 Professional-practice benchmark

Eight dimensions of translation-shop practice, each given a verdict of **SOUND** (well-designed for this audience, behaves as intended), **GAP** (a real, confirmed incompleteness that is not actively dangerous — self-healing, narrowly scoped, or low-frequency), or **RISK** (a real, confirmed defect reachable in ordinary multi-editor/multi-book operation, with a plausible consequence of stranded work, a cross-book boundary violation, or a non-technical user hitting an unguided dead end).

**1. Review states & four-eyes integrity — RISK.** *(MIXED: LIVE + CODE-READ)* Self-approval itself is sound — a deliberate, documented design choice matched exactly by code and confirmed live, and not the risk driver. The RISK comes from two places: first, three CONFIRMED-KEEP code findings (companion report #1 and #2, both high severity; #4, medium) show the book-scoped four-eyes boundary Unit 0 built everywhere else is simply absent on `pipeline.js` (inject/render/run gated by global role only, #1) and `sections.js` (approve/assign/request-changes, same pattern, #2; also an EDITOR-level upload route with no book scoping at all, #4, letting any editor write into any book's human-verified directories). Second, and LIVE-reproduced this session: the `discuss`/`rejected` segment-edit states have no resolution transition anywhere in code, sharpened from a documentation silence into a concrete, reachable failure — a raw SQL constraint error delivered via `alert()` to a head-editor doing ordinary work (§3, bug (a)).

**2. TM lifecycle — GAP.** *(MIXED: LIVE + CODE-READ; data-starvation restated as known, not fresh)* Project-wide TM thinness (one book with a 3-unit TMX, four books with none) is the already-documented state, restated here for context only. What this review adds: the auto-regeneration mechanism is real and does fire — confirmed both by code read and live, this session's own apply triggered it — but that same live call then failed silently for the fixture book (§3, bug (b), fixture-only). The mechanism working correctly for real books, and failing invisibly rather than loudly for an edge-case slug, together show that a TM-accumulation failure can occur with zero human-visible signal — worth noting precisely because TM is one of the project's three headline human-verified deliverables.

**3. Terminology governance loop — GAP.** *(MIXED: LIVE + CODE-READ)* The human-facing half is LIVE-verified end to end: create → approve → export-CSV all worked. But the machine-facing half that actually determines MT quality — the `glossary-unified.json` export `api-translate.js` reads — is CLI/cron-only with no route or scheduled-job wiring found anywhere in the repo; this review deliberately did not exercise it live to avoid mutating a real book's tracked file. Per the project's own MTPE framing, the glossary export *is* the asset that improves future MT quality — this is the load-bearing seam in the loop, and its automatic, ongoing operation is unconfirmed (though its on-disk date indicates it has run at least once). Compounding this, editors are told a stale CSV is "the authoritative source for approved terminology" when it has no live effect at all (§2).

**4. QA gates — SOUND.** *(MIXED: CODE-READ primary + LIVE supporting)* The advisory-not-blocking design for all four mechanical QA checks is a deliberate, well-matched choice for this audience: it defends against the MTPE-specific "fluent-but-wrong" reviewer risk without imposing translator-tool-style save friction. All four gates match documentation exactly; the spellcheck endpoint's graceful degradation with the sidecar absent was confirmed live, not just architecturally. One secondary caveat: the single genuinely hard gate (structural marker damage blocked on save) is enforced client-side only, with no equivalent server-side check — flagged as incidental/out-of-scope by the code review rather than adversarially verified, so it carries lower confidence, and it doesn't affect an editor using the documented UI.

**5. Reviewer/editor throughput ergonomics — GAP.** *(MIXED: LIVE + CODE-READ)* De-jargoning and role-hiding work as designed and are LIVE-confirmed: human titles in headers, pipeline panels genuinely hidden from the editor role (checked against live role state, not just source), and a clean named-actor conflict message. The dashboard "workflow trap" is LIVE-confirmed closed on the read side (§2/§3). The weak point is **SLA visibility**: the dashboard's "0 overdue" tile matched the API exactly this session, but a code finding shows `overdueCount` is hardcoded to `0` and never populated anywhere (companion report #28, low/KEEP) — the tile cannot currently distinguish "accurate because verified" from "accurate because structurally incapable of being anything else." The *structured* SLA-trackable queue also remains submit-gated even though basic visibility is not. A secondary note: a client-side retry queue can replay a stale failed save over newer, already-saved content under exactly the flaky-network conditions it exists to handle (companion report #8, medium/KEEP).

**6. Traceability & audit trail — GAP.** *(MIXED: LIVE + CODE-READ, leads from a confirmed live positive)* The core activity-log record is LIVE-verified high-fidelity and should anchor this dimension: the admin dashboard independently reproduced this session's exact action sequence in correct order, attribution, and plain Icelandic; `version_restored` entries were complete and correct in both directions of a live restore round trip. The GAP is in specific *views* of that otherwise-sound record: a chapter-level activity panel is completely non-functional due to a field-name mismatch between what the server sends and what the client reads (companion report #12, medium/KEEP), and six of eleven activity-log call sites — including approve/reject/unapprove — wrap the audit-write itself in a bare `catch {}`, so a four-eyes accountability entry can vanish with zero trace if the log write ever throws (companion report #21, low/KEEP). A live-discovered nuance worth naming precisely: version numbers are pre-write snapshots, not post-write results, so "version 1 = my first change" is backwards (§3).

**7. Rollback & recovery safety — RISK.** *(MIXED: LIVE + CODE-READ)* The flagship Unit 1 mechanism is LIVE-verified genuinely sound: a full restore round trip, both directions, was confirmed clean and byte-correct on disk, and the rebuild-from-history affordance was confirmed for both halves, not just its existence. A structurally similar apparent risk (writing the faithful file inside the DB transaction) was adversarially reviewed and refuted — atomic temp-plus-rename writes, a `.bak` backup, and rollback-and-retry all hold. The RISK is in paths adjacent to that flagship mechanism, reachable in ordinary multi-editor operation: "Vista + Birta" applies an edit to the faithful file *before* checking whether a same-chapter render job is already running elsewhere, so a collision leaves the edit applied-but-unpublished with a client-side retry that dead-ends on "already applied" (companion report #6, medium/KEEP); the Pass-2 approve step commits `status='approved'` before writing the localized file, so a write failure strands the edit in an approved-but-unapplied state recoverable only indirectly (companion report #3, downgraded high→medium but still CONFIRMED real). A narrower confirmed edge case: the restore snapshot mechanism excludes empty segments, so a segment that is empty now but had content in a target restore version cannot be returned to empty through a restore-then-undo round trip — a direct, confirmed break of the "restore is itself reversible" guarantee for that one case.

**8. Onboarding load — RISK.** *(MIXED: LIVE + document-comparison)* What the live system itself teaches a new **editor** is genuinely good and LIVE-confirmed across this entire session: role-gating hides pipeline vocabulary entirely, headers show human titles, every user-facing string encountered was plain Icelandic, and save/conflict states give honest, actionable feedback. The RISK is what a new **head-editor or admin** — or any editor who looks beyond the UI for help — would be told by the documentation corpus, which this review's own drift catalog found badly and in places actively wrong (§2, restated here for its onboarding consequence). Most consequential: `review-protocol.md`, a skill that **auto-triggers** on the exact topic of "discussing reviews or approvals," documents an entirely different, retired review model with no connection to the live system — this is not a rarely-read footnote, it is the exact document the tooling itself would surface. Compounding this for a non-technical audience specifically: this review's own live walkthrough surfaced a raw SQLite constraint message delivered verbatim via `alert()` to a head-editor doing ordinary work (§3, bug (a)), and a companion code finding shows a second, similar dead end — a head-editor clicking Inject/Render before a prerequisite stage completes sees only a bare "Villa: HTTP 409," with the server's actual explanatory text discarded client-side (companion report #14, medium/KEEP).

**Verdict tally: 1 SOUND (QA gates) / 4 GAP (TM lifecycle, terminology governance, throughput ergonomics, traceability) / 3 RISK (four-eyes integrity, rollback/recovery, onboarding load).**

## §6 Ranked recommendations

Ranked by (impact on editorial trust/onboarding) × (how reachable the underlying problem is in ordinary, non-adversarial use). Each is labeled **[JUDGMENT]** (this review's prioritization/recommendation) or **[FACT]** (the cited evidence it rests on). Findings shared with the companion code-review report are cited by number, not re-described in full — this section's contribution is the editorial-process framing, not a second copy of the finding list. Every recommendation stays inside the audience boundary: no proposal here adds translator-shop vocabulary, process ceremony, or save-time friction to the editor-facing UI.

1. **[JUDGMENT] Fix the documentation corpus's authority problem first — it is the cheapest available fix with the widest blast radius.** **[FACT]** `master-pipeline.md` self-declares "authoritative" while describing an entirely retired workflow (§2); `review-protocol.md` auto-triggers on "discussing reviews or approvals" per CLAUDE.md's own skill table yet teaches a different, retired review model (§2, §5 dimension 8); `terminology.md` calls a stale, disconnected CSV "the authoritative source" (§2, §5 dimension 3); CLAUDE.md's own documented `npm run update-status` command does not exist (§2). None of this requires touching a single line of application code or the editor UI — it is pure documentation triage (retire, relabel, or explicitly mark legacy), and the damage of leaving it stands compounds silently every time a new head-editor or admin is onboarded, or an existing one goes looking for how a feature is supposed to work.

2. **[JUDGMENT] Close the book-scoping gaps on `pipeline.js` and `sections.js` next — this is Unit 0's own established pattern, just missed on two route files.** **[FACT]** Companion-report findings #1, #2, and #4 (high/medium, CONFIRMED/KEEP after independent adversarial re-verification) show `pipeline.js` and `sections.js` gate cross-book-sensitive actions (inject/render/run; approve/assign/request-changes; file upload into `03-faithful-translation/`/`04-localized-content/`) on a global role check with no book-ownership intersection, while every comparable route elsewhere in the codebase already uses the correct `requireHeadEditorFor`/`requireBookAccess` pattern. This is an omission from a sweep that was otherwise thorough, not a design gap needing new architecture — the fix is applying an existing, proven pattern to two more files. It is listed here, not only in the code report, because a translation-shop review is specifically built to catch exactly this class of cross-book trust violation, and because as more books (biology, physics) come online with distinct head-editors, this becomes more reachable, not less.

3. **[JUDGMENT] Give the `discuss`/`rejected` segment-edit states a resolution path — this is a live, reproduced bug affecting a head-editor doing ordinary work, not a theoretical gap.** **[FACT]** No code path moves a `segment_edits` row out of `discuss` or `rejected` status; this was reproduced live this session as a raw SQLite `UNIQUE constraint failed` message delivered via a browser `alert()` (§3, bug (a); §5 dimension 1). The minimum fix — wrapping the save/discuss path in a `try`/`catch` that returns a clean, Icelandic, actionable message instead of the raw constraint text — removes the immediate user-facing harm without any state-machine redesign. The fuller fix (an explicit transition out of `discuss`, with a named owner, answering the project's own long-open question of who is responsible for resolving a discussed item) is a real design decision for the lead to make deliberately, not something to default into as a side effect of a bug fix.

4. **[JUDGMENT] Decide the module-submission button's fate on purpose — right now its behavior is an accident of half-finished work, not a decision anyone made.** **[FACT]** `dashboardReadModel` already solves "my work is invisible until I submit" on the read side, live-confirmed this session (§2, §3) — but the "Submit module for review" button is still live, unconditional, and now feeds only the narrower SLA-tracked queue, a fact documented nowhere. An editor today gets a button whose apparent purpose (make my work visible) is no longer accurate; it does something real but different and unexplained. This needs no new code — only a decision: relabel the button to describe what it actually still does, or finish the originally-planned work that would formally retire or gate it. Either resolution is fine; the current silently-half-migrated state is the actual problem, because it teaches editors an incorrect mental model of what "Submit" means.

5. **[JUDGMENT] Harden the audit trail's write path before its read-side views — a vanished accountability entry is worse than a blank display panel.** **[FACT]** Six of eleven activity-log call sites, including approve/reject/unapprove, wrap the audit-write itself in a bare `catch {}` while sibling call sites in the same files log correctly (companion report #21, low/KEEP) — a four-eyes accountability record can disappear with zero trace if the log write ever throws. Apply's own content-version snapshot carries no `applied_by` attribution, unlike restore's (§3, Mutating pass). Neither loses primary content — the faithful/localized files themselves are confirmed correctly written and byte-correct on restore — but both erode exactly the record a small team without a dedicated ops function would need most: reconstructing what happened, after the fact. The separately-real display-panel bugs (companion report #12, #26, #27) matter less than the write-path gap and can follow once the write path is trustworthy.

6. **[JUDGMENT] Spend two minutes checking whether the "Saga útgáfa" restore modal already disambiguates version-numbering before writing any code.** **[FACT]** Version rows are pre-write snapshots, not post-write results, discovered live this session — "version 1 = my first change" is backwards, and a head-editor restoring the lowest-numbered version could silently discard the newest approved edit instead of recovering an old one (§3, Mutating pass; §5 dimension 6). This review could not confirm at pixel resolution whether the modal's existing per-version diff view already makes this clear. If it does, no fix is needed beyond noting the mechanism in a place a head-editor would find it; if it doesn't, the fix is a one-line copy change ("this was the content *before* this version's edit"), not new logic — worth checking before it's worth building.
