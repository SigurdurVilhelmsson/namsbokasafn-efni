# kerning

## Headline

§C140 ⑥'s "per-run kerning" is actually TWO unfixed findings from two dates over two different populations of drawn text — kept English run-exact runs (6 named, needs a per-run font-kerning:none/normal choice) vs. all 647 translated+kept <text> elements in the final T23 build (28 affected, cosmetic-only, "not covered by any ruling"). Neither is implemented in the shipped code today.

## Findings

- FINDING A (2026-09-13, kept-English run-exact runs only). Source: experiments/figure-text-translation/evidence/2026-09-13-compose-fidelity/reports/2a-prototype.md §6.2: 'Of 394 multi-char Liberation runs, 29 contain kern pairs. 19: the position-derived adv equals hmtx + kern within 0.05 pt (so the source kerned them: Average atomic, 119.37, Avogadro's, A atoms). 6: adv equals hmtx without kerning (rxn2 Coefficient ×2, flowchart of A ×2, moleratio2 Avogadro's, exocytosis Vesicles). The rest are flowchart Tc/Tw runs. Chromium kerns by default: font-kerning:normal is a no-op, measured identical on all 19. Setting none on the 6 raises their block iou1 (rxn2 Coefficient 0.895→0.933; moleratio2 0.914→0.966).' All six runs belong to figures among the 34 bought (rxn2, flowchart, moleratio2, exocytosis all appear in the fractional/integral-page figure lists in evidence/2026-09-15-t23-review-fixes/PREDICTIONS.md).
- FINDING B (2026-09-15, T23 census residual, population spans ALL 647 <text> elements — both kept run-exact and translated layout). Three independent, verbatim-agreeing citations: (1) shipped code comment experiments/figure-text-translation/compose.py:163-170 — '...even then Chromium applies the font's kern table, which cairo does not: 28 of 647 segments on the 34 draw up to 0.99 pt short, which can only widen a gap. The DRAWING context is untouched, so kept blocks' raster does not change.' (2) figscripts.py:441-447 (split_at_word_edges docstring) — same number. (3) evidence/2026-09-15-t23-review-fixes/reports/round1-result.json .integration.concerns[5] and .review.minors[10], and round2-result.json .fix.changes[6-7] — 'Leftover from the browser census, pre-existing and not covered by any ruling... 28 of 647 segments draw up to 0.99 pt shorter than compose measured them. That can only widen a gap or pull a right edge in, never lose a space. Only Chromium 151 on Linux was measured.' Also carried in docs/superpowers/specs/2026-09-13-c140-t23-scripts-reflow-decimals-design.md:101 (Amendments — 2026-09-15).

The scratch tree the round-1/round-2 build used (/home/siggi/dev/scratch-c140/...) no longer exists on disk (confirmed by `ls`). Treat '28/647, up to 0.99pt' as a reported, thrice-repeated finding that is not independently reproducible from what's currently in the repo.
- Neither fix is implemented in shipped code. Confirmed by grep: no 'font-kerning' anywhere in experiments/figure-text-translation/{svgout,figtext,compose,figscripts,figlayout}.py except in comments describing the open problem.
- HOW 'unkerned in the source' is determined per run (finding A): NOT a stored flag in runs.json. It's computed by evidence/2026-09-13-compose-fidelity/instruments/2a/plusvariant.py:16-24 (kern_wanted(text,size,bold,italic,adv)), which compares the run's `adv` field (already present in every committed runs.json, produced by shipped readlayer.py) against two predictions from Liberation Sans's own font tables loaded via fontTools from /usr/share/fonts/truetype/liberation/*.ttf: h = sum of per-char hmtx advances (unkerned), k = sum of the font's own kern-table deltas for adjacent char pairs. Returns True (source WAS kerned) if adv is closer to h+k than to h alone, False if closer to h alone, None if <2 chars, an unmapped char, or no applicable kern pair (|k|<0.01).
- Critically, runs.json's `adv` is itself POSITION-DERIVED, not a naive per-char sum — readlayer.py:23-30 computes it as `along(last) - along(first) + adv(last)` specifically so it captures whatever Tc/Tw/TJ kerning the SOURCE PDF actually used (23 figures in the corpus carry such kerning). This means finding A's per-run test needs NO new data extraction — the required input (`adv`) is already in every committed runs.json; only the font-table comparison logic needs to move from evidence-only scratch code into a shipped module.
- HOW run-exact drawing positions glyphs TODAY: compose.py:77-102 (draw_run_exact) draws ONE ctx.show_text(text) call per RUN (not per glyph) — the whole run's string, positioned at ONE absolute (px,py) read from the run's own source-derived (x,y) via dev(). The SVG emits one <text> element per run with a single x/y attribute (compose.py:96-97) — no per-glyph positions, no textLength attribute anywhere in svgout.py. figtext.run_draw_text (figtext.py:263-290) just strips (cid:N) placeholders; it does not split into per-glyph pieces.
- WHY browser kerning still matters despite absolute per-run positions: each run is independently anchored (run B's x does not depend on run A's rendered width), so browser kerning cannot cascade into misplacing a DIFFERENT run — but it DOES change the internal glyph spacing WITHIN one run's single <text> string when Chromium shapes it, which is exactly finding A's 6-run defect (source drew that run unkerned; Chromium's default font-kerning:normal re-kerns it anyway, tightening the internal spacing).
- WHICH DRAWN RUNS ARE AFFECTED — finding A is kept-English-only by construction: plusvariant.py:44 only calls kern_wanted inside the `if bi not in kept: continue` branch, i.e. only for run-exact (kept) blocks. Finding B's denominator (647) spans BOTH populations (confirmed: PREDICTIONS.md 'text_count... 655→647 over the 34' is the whole SVG's <text> count including both path='run-exact' and path='layout' items; R14 measured 'the 614 <text> elements of the 33 non-flowchart figures' = 647-33). But the mechanism described in compose.py:169-170 ('The DRAWING context is untouched, so kept blocks' raster does not change') and the fact that lin_advance/seg_width (compose.py:172-236) — the LINEAR cumulative-width machinery whose mismatch with Chromium's kerning causes the '28' shortfall — is used ONLY to place translated 'layout'-path segments (each segment's x is the cumulative sum of the LINEAR widths of prior segments in that line; see the design's §1 'x advancing by the previous segments' widths') strongly suggests finding B is a translated/layout-path phenomenon: a kept run's kerning-shortened width has no downstream item positioned relative to it, so it can't manifest as 'the next thing's reserved slot is now too far right' the way a translated segment's can. I could not find a per-item breakdown in preserved evidence confirming this split directly — flagging it as the best-supported inference, not a directly-cited fact. evidence/2026-09-15-t23-review-fixes/instruments/census/census.py:34-40 (pairs()) DOES pair path='run-exact' items too (grouped by block+y, compared by x), so the census machinery isn't blind to the kept population even though its own printed boundary counters are 0 for the final build.
- CANDIDATE 1 — per-run/per-segment font-kerning:none 'chosen from the data' (finding A's own unshipped fix; plusvariant.py:57-60 splices style="font-kerning:{normal|none}" onto exactly the affected <text> elements). Measured effect on the 6 kept runs: rxn2 Coefficient iou 0.895→0.933; moleratio2 0.914→0.966 (2a-prototype.md §6.2). Effect on translated/re-flowed labels: N/A as designed for finding A — kern_wanted needs a source `adv` to compare against, which a freshly-composed Icelandic label does not have (there is no PDF source advance for text that was never in the source PDF). For translated segments the correct target is compose's own linear metric, which this candidate's TEST cannot supply — it would need to be extended with a rule like 'no source data → always none'.
- CANDIDATE 2 — a GLOBAL style (text{font-kerning:none} on the whole <style> block, or the attribute on every <text>). Not measured directly in evidence, but the 2a-prototype.md finding that the 19 correctly-source-kerned runs already match Chromium's DEFAULT (normal) kerning exactly implies this candidate would REGRESS those 19 (forcing 'none' removes kerning the source actually had). For translated labels this candidate is CORRECT and sufficient with no measured downside: since re-flowed Icelandic text has no source kerning state to preserve, matching compose's own linear/unkerned metric IS the correct target, and this fully closes finding B for the whole corpus.
- CANDIDATE 3 — x-per-glyph positioning (place every glyph at its own absolute x instead of one <text> per run/segment). NOT measured anywhere in the evidence — pure mechanism inference. Would remove the browser's opportunity to shape/kern multiple glyphs together regardless of any font-kerning CSS value. Heaviest change: reverses the deliberate 'one item = one element' design (svgout.py:16-22,56-67 for run-exact; figscripts.py's segment model for translated labels), inflates <text> element counts, and would need rework of test_figure_compose.py:717's <text>-content regex (already flagged as a hazard in COMPOSE-FIDELITY.md for the existing one-<text>-per-run design).
- CANDIDATE 4 — drop the kern table from the embedded font subset (change subset_face's opt.layout_features, currently ['*'] i.e. keep-everything, at svgout.py:16-20 (FACES dict, hard-coded /usr/share/fonts/truetype/liberation/*.ttf paths) and svgout.py:25,31 (subset_face)). NOT measured anywhere. Confirmed only that TODAY's shipped subset keeps every layout feature including the kern table (opt.layout_features = ['*']), so this is a real, currently-untaken option. Functionally equivalent to candidate 2 (global, unconditional no-kerning for every Liberation-drawn run/segment) since there would be no kern data left for any font-kerning CSS value to act on — same tradeoff: fixes finding B fully, regresses finding A's 19 correctly-kerned kept runs. STIX-drawn runs (mostly single symbol glyphs) were not checked for kerning relevance either way.
- VERIFICATION RENDERER: the reader-facing path is experiments/figure-text-translation/render-check.mjs, which loads the SVG via <img src=...> — its own docstring: '<img src=...> is how cnxml-render.js publishes every figure, and it is the strictest case: an SVG loaded that way is sandboxed and cannot fetch a stylesheet or a webfont... Rendering the file any other way — a viewer, an inline <svg>, a converter — tests something no reader will ever do.' This is Chromium via Playwright (server/node_modules/playwright), <img>-sandboxed.
- ⚠️ The census tool that MEASURED findings A/B does NOT use that renderer: evidence/2026-09-15-t23-review-fixes/instruments/census/cb.mjs inlines the SVG directly into the page DOM via pg.setContent(...), not via <img>. font-kerning and text-rendering are ordinary CSS properties with no external fetch involved, so there's no structural reason inline-vs-<img> would differ for kerning specifically — but this was not itself cross-checked in the preserved evidence (round 1 DID cross-check the geometricPrecision ruling's per-<g> vs per-<text> placement between inline and <img> rendering, '35/35 pixel-identical', per round1-result.json review.minors — no equivalent cross-check is recorded for font-kerning). A verification should either re-run the measurement through render-check.mjs's <img> harness, or explicitly re-establish inline/<img> agreement for font-kerning.
- What a verification needs to measure once a fix is chosen: (1) finding A's 6 runs (or their recomputed equivalent from current runs.json + font tables) — per-run block IoU vs PDF-true source ink, before/after, reusing evidence/2026-09-13-compose-fidelity/instruments/1a/fidelity.py and .../2a/bscore_mixed.py; (2) finding B — reconstruct census.py's per-item self-check (not preserved standalone) or extend items.json to carry each item's own compose-predicted linear width, then re-run census.py's existing boundary classifier and confirm lost/narrowed/collision/overhang stay at 0 (the regression control the 2026-09-15 build already established in reports/census-final.txt); (3) an explicit positive-control re-measurement of the 19 correctly-kerned kept runs under whichever fix is chosen, rather than assuming the 'no-op' framing still holds; (4) Firefox/WebKit remain explicitly out of scope in every piece of this evidence ('only Chromium on Linux was measured' — 2a-prototype.md §5, round1-result.json concerns, figscripts.py:441-447) — no need to add them, but keep stating the limitation.

## Open questions

- Does §C140 ⑥ need to fix finding B (28/647, cosmetic 'can only widen a gap') at all, or is it explicitly out of scope the same way Firefox/WebKit are? The register row's own wording ('per-run kerning') most literally names finding A (the 6 kept runs); finding B was logged as 'not covered by any ruling' when R12-R15 shipped.
- If both findings are in scope: is a single mechanism wanted (e.g. 'always none for translated segments; per-run choice via kern_wanted for kept runs' — candidate 1 generalised with a source-data-absent fallback), or two separate, independently-shippable patches?
- kern_wanted's Liberation Sans font-table dependency currently lives only in throwaway evidence code with hard-coded paths (/usr/share/fonts/truetype/liberation/*.ttf) duplicating svgout.py's own FACES dict (svgout.py:16-20) — a shipped implementation needs one shared source for these paths, not a second copy.
- Whether subset_face's opt.layout_features=['*'] (svgout.py:31, candidate 4) should change is coupled to whichever global-vs-per-run decision is made; it was not evaluated in any evidence file found, and its interaction with STIX-embedded runs (does STIX carry/need kern data at all?) was not investigated.
- The exact instrument behind '28 of 647... up to 0.99pt short' is not reproducible from what's preserved in the repo (its scratch tree is gone) — before relying on that number for a design decision, consider whether it's worth re-measuring fresh (and whether that re-measurement should also finally report a kept-vs-translated breakdown, which the original apparently didn't).
