- TASK 1 — redistributing the font file + OFL text in a public repo. The repo is public (CLAUDE.md § 'THIS REPOSITORY IS PUBLIC (since 2026-07-25)'), and its own licence table puts experiments/ under MIT, owned by root LICENSE (CLAUDE.md:121). Committing an OFL font under experiments/ is a new boundary that table does not yet name. STIX 1.x ships NO OFL.txt — the licence document in the archived 1.x releases is one PDF, 'STIX Font License 2010.pdf' (data/licence-research.json:356-363, sha256-identical across STIXv1.0.0/1.1.0/1.1.1); a plain-text sibling exists only inside 1.1.1's stix-tds folder (json:362). So 'commit the OFL text' for STIX 1.x means committing that PDF or its text sibling, not a root OFL.txt the way Liberation ships one. What the evidence quotes on committing a font + licence into a public repo: FAQ 3.8 (quoted inside claim verdict, json:153): "Making a public commit or publishing a public branch is effectively redistributing your modifications, so any change to the font will require that you do not use the RFNs." OFL condition 2 (json:239): copies bundled/redistributed/sold with software must each contain the copyright notice and licence, acceptably in machine-readable metadata 'as long as those fields can be easily viewed by the user.' OFL condition 5 (json:33-38): the Font Software 'must be distributed entirely under this license, and must not be distributed under any other license.' FAQ 1.11 (json:79): distribution not counting as 'embedding' 'needs to be accompanied by any copyright notices and licensing information available in OFL.txt.' FAQ 1.15 (json:250), on a font travelling unmodified inside a document's file structure: 'The OFL does not allow anyone to extract the font from such a structure to then redistribute it under another license. … Even if the font travels inside the document as one of its assets, it should not lose its authorship information and licensing.' None of these settle whether committing the subsetted/renamed font under experiments/ (separately from shipping it inside the composed SVGs) needs different treatment — not addressed by any of the 50 claims or 16 unresolved entries (closest are U2/U3, json:583-584, about the SVG case).
- TASK 2 — reserved-name requirement, quoted. OFL condition 3 (json:135-137, quoted README.md:56-58): 'No Modified Version of the Font Software may use the Reserved Font Name(s) unless explicit written permission is granted by the corresponding Copyright Holder. This restriction only applies to the primary font name as presented to the users.' FAQ 5.3 (json:157-159): the 'primary font name' restriction 'applies to the font menu name and other mechanisms that specify a font in a document.' A text mention of the original font's name is fine 'in the description field, in your modified source file or in documentation … as long as no one could be confused that your modified source is the original,' but 'you cannot use the Reserved Font Names in any way to identify the font to the user.' FAQ 5.4 (json:402-404): 'You may not use individual words from the Reserved Font Names, but you would be allowed to use parts of words, as long as you do not use any word from the Reserved Font Names entirely.' STIX's own reserved names (json:367-369 'STIX Fonts'; json:378-380 'TM Math'; README.md:47): STIX 1.x reserves 'STIX Fonts' (STI Pub Companies) and 'TM Math' (MicroPress); STIX Two's current OFL.txt reserves only 'TM Math' (json:447-449), while the 2.0.x licence PDFs — one of which stixfonts.org still links (json:514-522) — reserve both (json:470-478). README's own mapping of 'primary font name' to concrete fields (README.md:97-99, explicitly marked as OUR mapping, not the texts'): name records IDs 1, 3, 4, 6, 16, 17, 21, 22, and, in an SVG, the CSS font-family. FLAGGED GAP (not resolved here): the ruling's wording is narrower than FAQ 5.4. [USER]'s ruling (register:24-25) bars a family name containing 'STIX' or 'TM Math' as whole phrases; FAQ 5.4 bars 'individual words from the Reserved Font Names' entirely — so on that reading a family such as FigFonts, FigMath, or FigTM would contain an individual reserved word ('Fonts', 'Math', 'TM') while containing neither 'STIX' nor 'TM Math' as written. This is a real gap between the ruling's literal text and the FAQ's stricter reading — needs [USER]'s confirmation, not resolved here.

- TASK 3 — seven concrete placements for OFL licensing information, each followed by the evidence's own words (not a ruling on sufficiency): (1) Name IDs 13/14 inside the embedded font — condition 2 (json:239) 'as long as those fields can be easily viewed by the user'; FAQ 1.10 (json:226-228) a link alone is 'legally sufficient' but 'strongly recommend[s] against' it; neither text says whether a base64-embedded font's name table counts as 'easily viewed' — not addressed by any of the 50 claims. (2) WOFF2's own extended-metadata block — named only in the FAQ's WEBFONT discussion, not its embedding discussion: FAQ 2.2/2.2.1 (json:558-566) discusses 'WOFF-specific metadata' staying 'unaltered' for a CONVERSION to count as non-modifying; it does not say a metadata block satisfies condition 2's licensing-information requirement for an embedded subset. Production svgout.py's current subsetting does not touch this block at all. (3) An XML comment in the SVG — not mentioned by any fetched text; trivially 'easily viewed' by anyone reading the source, but no evidence basis either way for calling a comment 'metadata' in condition 2's sense. (4) <metadata> element in the SVG — not mentioned by any fetched text; SVG's own <metadata> is the closest markup analogue to a 'machine-readable metadata field,' but no fetched text was tested against SVG at all (U2/U3, json:583-584). (5) <desc>/<title> — not mentioned; these are user-agent-exposed (accessible-name) elements, arguably closer to 'easily viewed by the user' than a comment or <metadata>, but again no fetched text discusses SVG specifically. (6) A sibling file (e.g. an OFL.txt next to the SVG) — condition 2 itself lists 'stand-alone text files' as one acceptable form (json:239); the one placement the licence text names explicitly, though written for a font FILE with siblings, not an SVG.
