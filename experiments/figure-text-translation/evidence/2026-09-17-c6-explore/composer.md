# composer

## Headline

The composer draws every run in a hardcoded 'Liberation Sans'/'FigIS' family regardless of the source font, even though the field needed to tell a STIX run from a Liberation one already exists and is already read elsewhere (figscripts.py). The 2026-09-13 'Plus' prototype fixed this only for the run-exact (kept) population by extracting glyphs from each source PDF - a route the 2026-09-16 licence ruling has since replaced with the archived official STIX 1.1.0 file, itself verified only for the Regular face.

## Findings

- Q1 files/flow: experiments/figure-text-translation/compose.py is the driver; figtext.py (grouping, run_face); figscripts.py (script/italic transfer, symbol-font detection); figcontainers.py/figlayout.py (translated-path layout only); figcolour.py (CMYK-to-RGB, unrelated to font); svgout.py (SVG plus woff2 embedding); figure-compose.py (Node wrapper, verdict reader only).
- Q1 font family is hardcoded, not source-derived: compose.py line 70 sets FAMILY = 'Liberation Sans'. Every draw call uses this one constant - draw_run_exact (kept/identity, run-exact) at compose.py lines 106-108 via ctx.select_font_face(FAMILY, ...); setfont (translated/layout path, per line) at compose.py lines 138-142; setfont_st (translated/layout path, per styled segment, section C140-2) at compose.py lines 150-161; the measuring context in lin_advance at compose.py lines 180-192.
- Q1 weight/style come from two independent BaseFont substring lookups, never from family: compose.py line 74 builds a module-level BOLD set (bold in v[base].lower(), feeds the layout path) and figtext.run_face() (figtext.py lines 243-260, feeds draw_run_exact) returns (bold,italic) from bold/italic/oblique substring checks. Neither reads or branches on family.
- Q1 woff2/@font-face: svgout.py lines 16-21 define FACES mapping (bold,italic) to one of the four on-disk LiberationSans TTFs (Regular/Bold/Italic/BoldItalic) - the only font source svgout.py knows. svgout.py line 22 sets FAMILY = FigIS, the local CSS family name embedded in the SVG (chosen not to collide with an installed family). subset_face() (svgout.py lines 25-42) uses fontTools.subset.Subsetter (layout_features=[*], desubroutinize=True, drops DSIG, notdef_outline=True), subsetting to the exact character set a (bold,italic) combo actually draws, then sets font.flavor to woff2. write_svg() (svgout.py lines 49-98) emits one @font-face rule per used face only (lines 57-68) inside one style block, then one text element with font-family FigIS per drawn item (lines 79-92).
- Q1 text-rendering/font-kerning: text-rendering=geometricPrecision is written once, as a presentation attribute on the g element wrapping every text element (svgout.py line 78), per ruling R12 (docs/superpowers/specs/2026-09-13-c140-t23-scripts-reflow-decimals-design.md line 89, USER 2026-09-15) - this is the already-built half named in the task. font-kerning is written NOWHERE in the shipped svgout.py - confirmed by reading the whole file; no font-kerning attribute or style exists at all. That is the still-open half of item 6-2: Chromium applies Liberation Sans's own kern table by default, cairo's PNG path never kerns, and 6 of 34 corpus runs were positioned by the source PDF without kerning (design doc lines 100-102: 28 of 647 segments draw up to 0.99 pt short, which can only widen a gap; the same finding is restated in code comments at compose.py lines 164-171).
- Q1 COMPOSER_VERSION relation: tools/lib/figure-text-sidecar.cjs line 30 sets COMPOSER_VERSION = 3, with the docstring just above it (lines 20-23) reading: Bump when a composer change alters pixels for unchanged text. Doing so invalidates every stored renderHash, which correctly sends every approved figure back to mt-preview until re-reviewed. Mechanically computeRenderHash(blocks, composerVersion) (lines 63-73) hashes the version string itself; editorialState() (lines 84-90) recomputes it under the current COMPOSER_VERSION and compares to the sidecar's stored renderHash, returning mt-preview on any mismatch; effectiveState() (lines 116-122) is gated the same way. figure-run.js's isStale() treats composedVersion not equal to COMPOSER_VERSION as stale. So bumping the version to ship STIX/kerning demotes every currently-approved figure and requires a figure-run --stale pass (never a bare run) to recompose them. tools/__tests__/figure-run-paid.test.js line 1737 already contains a describe block named 'a COMPOSER_VERSION bump recomposes ONCE, not for ever' that pins exactly this mechanism.
- Q2 - yes, the source font IS knowable at compose time, via fields already read elsewhere. meta.json's fonts dict is keyed by the same scope-qualified key each run object's font field in runs.json carries; each entry carries base, the raw PDF BaseFont string, e.g. slash-ABCDEF-plus-STIXGeneral-Regular (built in readlayer.py, e.g. the dict(base=str(fobj.get(BaseFont,'')),...) construction at readlayer.py line 261, and again at readlayer.py line 671 inside resolve_font's UNSCOPED fallback).
- Q2 figtext.run_face(run, fonts) (figtext.py lines 243-260) already reads fonts.get(run[font],{}).get(base,''), strips the leading slash and the six-letter subset prefix (lines 258-259), and returns (bold,italic) in a family-agnostic way - it behaves the same whether base is LiberationSans-Italic or STIXGeneral-Italic.
- Q2 figscripts.py goes further and already DOES detect family, for a different purpose: _base_name(run,fonts) (figscripts.py lines 66-72, same stripping) feeds is_symbol_run(run,fonts) (lines 75-78) against a SYMBOL_FONT regex matching stix, symbol, mathematicalpi, mathpi, mt extra, cmsy or cmmi (line 52). This is already load-bearing production code: it decides which runs cast no vote for a line's base size (lines 21-23, body_size at lines 109-128) and which runs are candidates for sub/superscript/italic style transfer (section C140-2). Neither compose.py nor svgout.py imports is_symbol_run or _base_name today (checked directly: neither name appears in either file) - so the missing piece is a draw-time branch in compose.py's setfont/setfont_st/draw_run_exact plus a matching face table in svgout.py that reuses this existing detector, not a new detection mechanism.
- Q3 - the Plus prototype lives at experiments/figure-text-translation/evidence/2026-09-13-compose-fidelity/instruments/2a/ (files stixface.py and plusvariant.py), documented in the sibling reports/2a-prototype.md and summarized in COMPOSE-FIDELITY.md lines 91-131 and 166-175.
- Q3 glyph source (2026-09-13, now superseded): stixface.embedded_stix(pdf_path) (stixface.py lines 14-32) opens the figure's own source PDF with pikepdf and finds the single font object anywhere in the PDF whose BaseFont contains STIX (first match, per its own docstring), pulling raw CFF bytes from FontDescriptor/FontFile3 plus FirstChar, Widths and any Differences encoding. build_otf() (stixface.py lines 34-78) decompiles the CFF via fontTools.cffLib.CFFFontSet, redraws every glyph charstring, maps advance widths from the PDF's own Widths array (not the font's original hmtx), and assembles a fresh OTF via FontBuilder with family FigSTIX (the default; plusvariant.py never overrides it) and only ONE face, Regular (fb.setupCFF call at line 71). Nothing in this file builds Italic/Bold/BoldItalic STIX faces. Only STIXGeneral-Regular was ever extracted or measured this way, confirmed by reports/1d-completeness.md line 68 (only 4 base families on the 34, ...STIXGeneral-Regular): on the 34 bought figures no STIX Italic/Bold/BoldItalic run exists at all.
- Q3 what it wrote: plusvariant.py's build() (lines 36-85) calls the real, unmodified svgout.write_svg first (embeds only Liberation under FigIS), then POST-PROCESSES the SVG text with string replacement of font-family FigIS to font-family FigSTIX for every item flagged stix (line 69), and injects one extra @font-face rule for FigSTIX built from stixface.build_otf()'s single Regular face (lines 77-82). font-kerning is applied the same way, via a style attribute of font-kerning normal or none injected per text element (lines 70-71), but ONLY for items whose base name contains liberation (line 55) - STIX runs never get a kerning decision from this function. kern_wanted() (lines 21-29) compares a run's own positioned advance against Liberation's hmtx alone versus hmtx plus kern (loaded from the real Liberation TTFs' own kern table into a LIB dict at lines 16-19) and picks whichever matches the source PDF's actual spacing. A CSS rule text{text-rendering:geometricPrecision} is also added (lines 75-76) - a second, independent way of setting geometricPrecision compared to the shipped g-element attribute; that part has since shipped as ruling R12 via the g attribute instead.
- Q3 important naming problem: the prototype's chosen family FigSTIX contains the literal string STIX. Per evidence/2026-09-16-stix-licence/README.md lines 96-100, the governing USER ruling requires a family name containing NEITHER STIX NOR TM Math - so the prototype's own naming choice does not meet the ruling and must be renamed before reuse. Separately, stixface.build_otf() sets only FullName on the CFF top dict and familyName/styleName in the name table (stixface.py lines 71 and 74), carrying NO copyright/trademark/OFL-licence text at all (README.md lines 108-110 explicitly note this) - a second reason build_otf cannot ship unchanged, since the ruling also requires keeping copyright/trademark notices and OFL licensing info in the SVG.

Full plus variant (STIX plus geometricPrecision plus kerning), symfont group, absolute-numbers table (lines 153-154): run_cno_max in px is 2.00 for current, 2.00 for proto, 0.20 for plus; run_iou1_min is 0.38, 0.38, 0.88. This is the exact 2.0-to-0.2px figure named in the task. Scope: 47 runs across 45 blocks in 10 figures (of the 34 bought), of which 42 blocks are in the KEPT population in translated-mode runs (line 168 heading). Cost note at line 258: plus, translated mode, adds 9 STIX faces at 600-700 bytes each on top of proto's baseline.
- Q3 reusable versus extraction-dependent: NOT reusable - stixface.embedded_stix()'s whole mechanism of opening each figure's own source PDF with pikepdf and rebuilding a CFF glyph-by-glyph from the PDF's Widths array; the licence evidence establishes the accepted route is now subsetting the ARCHIVED OFFICIAL STIX 1.1.0 file instead (evidence/2026-09-16-stix-licence/README.md lines 150-151 give the STIXv1.1.0/Fonts/STIX-General/STIXGeneral-Regular.otf URL), verified byte-for-byte-equivalent in outline, advance and Notice against 162 of 162 real corpus STIXGeneral-Regular subsets (README.md line 37). Reusable - the woff2-embedding/@font-face plumbing itself (subset to woff2 to base64 data URI to per-face @font-face rule) is the same shape svgout.py already uses for Liberation, so extending svgout.FACES/subset_face to a second family is a natural generalisation, not new machinery; the kern_wanted() decision rule (compare source-positioned advance against hmtx versus hmtx-plus-kern) is reusable as the per-run kerning rule, though its Liberation-only kern-table lookup would need adapting or could simply stay Liberation-only since STIX runs get no kerning decision in the prototype either. Not yet done for a real implementation: per README.md lines 135-144's own Limits section, only the Regular official file was fetched and verified - Italic, Bold and BoldItalic STIX faces were never sourced from the official archive or compared at all, even though they exist corpus-wide (see next finding).

## Open questions

- Corpus-wide STIX exposure is not broken down by kept-versus-translated at the family level in reports/1b-census.md - only the 34-figure 1d census has that granularity. A ship decision covering more than the 34 bought figures would need that split re-measured before scoping the fix.
- Neither the 2026-09-13 prototype nor the 2026-09-16 licence evidence sourced or verified an official STIX 1.1.0 Italic, Bold or BoldItalic face - only Regular was fetched and compared. Corpus-wide these three faces cover 444 of 883 STIXGeneral blocks (over half), so extending beyond Regular is open work, not a checked extension of the prototype.
- The prototype's family name FigSTIX and its build_otf()'s bare name table (no copyright/trademark/OFL text) both fail the 2026-09-16 ruling's strict requirements (no STIX or TM Math in the name; keep copyright and trademark notices; keep OFL licensing info in the SVG) - a real implementation needs a new naming scheme and a build_otf() that preserves those name-table records, neither of which exists in any evidence file read.
- Whether a per-run font-kerning attribute, once shipped, needs its own resolver/test analogous to test_svgout.py's resolved_text_rendering (which currently only tracks text-rendering) was not settled - no existing test parses font-kerning at all.
- figure-compose.py, figcontainers.py, figlayout.py and figcolour.py were only grepped/cited for fields relevant to the five questions, not read in full - a future session needing the container/layout mechanics themselves would still need a full read of those files.
